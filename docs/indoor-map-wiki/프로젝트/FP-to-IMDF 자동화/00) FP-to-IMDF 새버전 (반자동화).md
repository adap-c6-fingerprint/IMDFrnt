4. 사용자는 사이드 바에서 현재 도면 SVG로부터 추출하고 싶은 property type의 **'레이어 생성하기' 버튼**을 눌러, 새로운 레이어를 추가한다.

	- 버튼 라벨은 상태에 따라 바뀐다: 레이어 없음 → `레이어 생성하기`, 이미 있음 → `레이어 열기`, 현재 활성 → `사용 중`(버튼 아님).
 해당 레이어에는 상위 기본 레이어와 같이, 도면의 모든 벡터 개체가 포함된 레이어가 생성된다.
	1) 다른 property type 레이어에서 이미 'feature로 저장'된 개체는, 동일하게 현재 레이어에도 포함되어 생성되기는 하나, 선택할 수 없고 비활성화된다.
	   
		- 해당 개체를 사용자가 선택하려고 하면, 경고창 띄우기. "이미 {기존 저장된 property type} 레이어에서 {feature 그룹 임시 일련번호}으로 저장된 레이어입니다. 이 개체를 {현재 property type}으로 바꾸려면, {기존 저장된 property type}에서 저장을 해제하세요."
		  
			선택지 1) "{기존 저장된 property type} 레이어로 이동" >> 해당 레이어로 이동 후, 선택하려는 개체가 포함된 feature 그룹으로 이동. 이동 시 해당 feature 그룹만 선택되고 다른 개체는 비활성화된 상태로.
			선택지 2) "현재 레이어로 돌아가기"
   
5. property type 레이어가 생성되면, 사용자는 직접 벡터 개체 하나하나를 선택해 그룹화한다.
	- 그냥 클릭하면 선택되지 않음
	- (fn+shift+z) 누른 상태로 클릭해야 선택됨
	- 그냥 드래그는 **화면 이동(팬)**. 단 드래그 시작점이 **지금 선택된 개체 위**면 그 개체(들)의 이동이다(2-3 참조, 2026-08-25 2차 재도입) — 선택되지 않은 곳에서의 드래그는 계속 팬이다.
	- **(fn+shift+z) 누른 상태의 드래그는 사각형 다중 선택**(2026-08-25 변경, 디버깅 9번). 종전의 "드래그 다중 선택 불가"를 뒤집은 것이다. 수식키 없는 드래그가 팬이라는 규칙은 그대로이므로, 실수로 선택되는 일은 여전히 없다.
		- 좌 → 우 드래그: 사각형 안에 **통째로 들어온** 개체만 선택
		- 우 → 좌 드래그: 사각형에 **닿기만 해도** 선택 (화면 밖까지 뻗은 벽선을 고르는 유일한 길)
		- 드래그 선택은 **더하기**다. 이미 고른 것은 풀리지 않는다.
		- 보조 개체 제외 창은 클릭이 수식키 없이 먹으므로 **드래그도 수식키 없이** 사각형 선택이다. 그 창의 화면 이동은 ⌥드래그·두 손가락 스크롤.
	- shift 눌러 다중 선택은 여전히 불가능.
	- (fn+shift+z)누르면 현재 선택된 개체 이외에 다른 개체는 70% opacity 처리
	- 선택 해제도 (fn+shift+z)

	3) 펼친 feature에 대한 액션
		1) 상위 type property가 요구하는 변수 목록을 각각 슬롯에 표시 (타입 변경 불가) / 변수 목록은 02) Projects/06) Challenge 6/02) FP-to-IMDF 자동화/무제 참조
		2) id는 입력할 수 없도록 함 (추후 파일 변환 단계에서 한번에 자동 입력)
			- **OGC IMDF 1.0.0 Reference 원문 확인):** Feature의 id는 "globally unique, RFC 4122 compliant **version 4** UUID"여야 한다(MUST). 따라서 변환 단계에서 `UUID()` v4로 자동 발급한다.
			- 같은 스펙이 강제하는 두 가지 제약:
				1) "MUST be retained to identify the target feature during the lifetime of its existence across distinct deliveries" — **한 번 발급한 UUID는 다시 내보낼 때도 유지**되어야 한다. 즉 내보내기마다 새로 발급하면 스펙 위반이므로, 발급된 UUID를 프로젝트 파일에 영구 저장한다.
				2) "MUST NOT be re-assigned to another Feature of any type" — 휴지통으로 보낸 feature의 UUID를 다른 feature가 물려받아서는 안 된다.
			- 근거: `01) Wiki/01-3) 위키 -------------------/A. 가공된 지식/A-06) Indoor Map/A-06-01) Indoor Map Overall/10) 지오레퍼런싱 기준점 — 몇 개를 왜 찍어야 하는가.md`, `01-2) 소스 .../S06-02) FP-to-IMDF/src13. 지오레퍼런싱 기준점 최소 개수·Feature id UUID 요건 조사.md`

			2) 점 찍으면 자동으로 벡터 좌표 생성. 추후 geojson으로 파일 변환시 다음과 같이 json 반환:

				- **(2026-08-25 확정) 두 선분이 '만나는 점' 없이 서로를 가로질러 지나가는 경우, 교차점을 지나쳐 찍힌 끝점은 좌표에서 뺀다. 그 교차점이 링의 꼭짓점이다.** (디버깅 5번) 모서리마다 선을 조금씩 지나치게 그린 도면(`#`자 사각형)에서 꼬리 끝점이 그대로 들어가면 방 폴리곤이 별 모양으로 삐져나오기 때문.
				- 단 다음 두 경우는 위 원문대로 끝점을 **유지**한다. ① T자 접합 — 한쪽 끝점이 상대 선분 위에 얹힌 것뿐이라 지나친 꼬리가 없다. ② 그 끝점이 다른 선분의 끝점과 맞닿아 있는 경우 — 작도 흔적이 아니라 실제 접합이다.

		2) 버튼 클릭 시 곡률에 맞춰 자동으로 선분화된다.
		3) 결과는 하나로 이어진 폴리라인이 아니라 **개별 선분들**로 표시된다.
			- 각 선분은 곡률 지점에서 서로 반드시 **만나야** 한다 (끝점이 어긋나 벌어지면 안 됨).
			- 각 선분은 만나는 지점을 벗어나 **교차해서는 안 된다** (끝점끼리 접할 뿐, 선분 내부를 가로지르면 안 됨).
		4) 선분화는 실행 취소 가능하다. 3-3) '곡선 개체만 따로 보기' 창에서 곡선 개체 단위로 '선분화 해제'도 가능하다.
9. Anchor 지정 — 전용 화면

	- **설계 확정(2026-08-24):** Anchor는 도면의 모든 좌표를 위경도로 바꾸는 기준이 되는 점이다. 개체 그룹화 작업과 성격이 달라 **전용 화면**에서 지정한다.
	- **용어:** 이 화면의 Anchor와 3항 좌측 사이드바의 `anchor` property type 메뉴는 화면이 분리되어 있어 혼동되지 않는다. 각각의 역할은 9-5)에 정리한다.

	1) 진입
		- 좌측 사이드바 최상단, property type 목록 **위**에 구분선을 두고 'Anchor 지정' 버튼을 둔다.
		- 시트가 아니라 **전체 화면 전환**이다. 작업 시간이 길고 지도 조작에 넓은 화면이 필요하기 때문.
		- 이 화면에 있는 동안 개체 선택·그룹화는 잠긴다. (2026-08-25: 위치이동 폐지로 문구에서 뺌)

	2) 화면 구성 — 좌우 분할
		- 왼쪽: 도면(SVG 캔버스). 줌·팬 가능.
		- 오른쪽: 지도(MapKit). 위성 뷰가 기본.
		- 하단: Anchor 목록 + 잔차 표시.

	3) Anchor 하나는 **두 개의 점이 짝을 이룬다**
		1) 도면 위의 점 — 사용자가 왼쪽 캔버스에서 클릭. 십자 마커가 찍히고 오른쪽 지도가 활성화되며 "지도에서 같은 지점을 클릭하세요" 안내 표시.
		2) 실제 세계의 같은 지점 — 사용자가 오른쪽 지도에서 클릭. **또는 위경도를 직접 입력.**
			- 위경도 직접 입력 경로는 선택지가 아니라 **동등한 주 경로**다. 대상 건물의 위성 이미지 해상도가 부족하거나, 측량 성과·지적도 좌표를 이미 갖고 있는 경우가 흔하기 때문.
		3) 양쪽 마커 모두 드래그로 미세 조정 가능.
		4) 각 Anchor에 라벨(사용자 메모)을 붙일 수 있다. 예: "건물 남서 모서리".

	4) 필요한 개수와 이유
		- Anchor 쌍 하나는 방정식 2개(x 일치, y 일치)를 준다. 따라서 필요한 최소 쌍 수 = 변환식의 미지수 개수 ÷ 2다.

		| 변환 | 허용하는 변형 | 미지수 | 최소 쌍 |
		|---|---|---|---|
		| 평행이동 | 밀기만 | 2 | 1 |
		| 상사(similarity) | 밀기+회전+균일 확대축소 | 4 | 2 |
		| 어파인(affine) | 상사+비등방 축척+기울임 | 6 | 3 |
		| 투영(projective) | 어파인+원근 왜곡 | 8 | 4 |

		- 1쌍만으로는 도면을 그 지점에 갖다 놓을 수만 있고 **회전각과 축척을 결정할 수 없다.**
		- 2쌍이면 두 점 사이 거리 비로 축척이, 두 점을 잇는 선의 방향 차로 회전각이 나온다(상사 변환).
		- 3쌍이 필요해지는 경우는 도면이 가로세로 다른 비율로 늘어났거나 기울어져 있을 때다(어파인 변환).
		- **확정: 최소 3쌍을 요구한다.** 전용 화면이 생겨 클릭 부담이 낮으므로 어파인 기준을 적용한다. SVG는 벡터라 원근 왜곡이 없으므로 투영 이상은 쓰지 않는다.
		- **4쌍 이상을 권장한다.** 3쌍 정확히면 미지수 수와 식 수가 같아 잔차가 항상 0이 되고, 사용자가 점을 잘못 찍어도 검출할 방법이 없다.
		- 근거: Esri 공식 문서 "three for a first-order affine", "A minimum of four links are required"(projective) 등. 상세는 `01) Wiki/.../A-06-01) Indoor Map Overall/10) 지오레퍼런싱 기준점 — 몇 개를 왜 찍어야 하는가.md`

	5) 정합 확인
		1) **2쌍이 모이는 순간 도면이 지도 위에 반투명하게 자동 오버레이**된다. 눈으로 맞는지 즉시 확인할 수 있다. '도면 겹쳐보기' 토글로 껐다 켤 수 있다.
		2) 마커를 드래그로 조정하면 오버레이가 실시간으로 따라 움직인다.
		3) 3쌍부터 **쌍별 잔차(residual)를 m 단위로 표시**한다. 특정 쌍의 잔차만 유독 크면 그 점을 잘못 찍었다는 신호다. 전체 RMS 오차도 함께 표시.
		4) 정확히 3쌍일 때는 잔차가 전부 0으로 계산되는데, 이는 정확하다는 뜻이 아니라 **판정할 정보가 없다**는 뜻이다. 0으로 표시하지 말고 `'판정 불가 (Anchor 4쌍 이상 필요)'`로 표시한다.
		5) 배치 안내 문구를 노출한다: "Anchor를 한쪽에 몰아 찍지 말고 도면의 각 모서리 근처에 하나씩, 내부에도 몇 개를 두세요." (Esri 공식 권고 "spread the links over the entire raster dataset... at least one link near each corner... and a few throughout the interior.")

	6) Anchor 선정 기준
		- 도면과 실제 지도 **양쪽에서 똑같이 특정 가능한 지점**이어야 한다.
		- 적합: 건물 외벽 모서리(가장 정확), 주 출입구 중심, 외부 돌출 구조물 모서리, 도면에 그려진 외부 포장·보도의 교차점.
		- 부적합: 방 한가운데, 가구, 실내 벽 교차점 — 위성 이미지에서 찍을 수 없다. 나무·차량 옆 — 시점에 따라 위치가 바뀐다.
		- 고층 건물은 위성 촬영 각도 때문에 옥상이 옆으로 밀려 보이므로 **지면 접합부**를 찍는다.

	7) 반영
		- Anchor가 3쌍 이상 확정되면 모든 property type의 좌표 표에 위경도가 즉시 채워진다.
		- 3쌍 미만이면 위경도 열 전체 비활성 + 'Anchor 미지정' placeholder, 내보내기 버튼도 잠긴다.
		- Anchor 쌍 목록은 프로젝트 파일에 저장된다. 도면 좌표와 위경도를 **함께** 갖는 유일한 데이터다.

	8) 3항 사이드바 `anchor` 메뉴와의 관계

		| | Anchor 지정 화면 (9항) | 사이드바 `anchor` 메뉴 (3항) |
		|---|---|---|
		| 목적 | 도면↔지도 대응 쌍으로 변환식 산출 | unit에 속한 IMDF Anchor Feature 생성 |
		| 좌표 | 사용자가 직접 지정 (도면 좌표 + 위경도) | 변환식으로 자동 계산, read-only |
		| 개수 | 3~5개 | 주소·입주자 수만큼 |
		| 산출물 | 프로젝트 파일 (변환식의 입력) | `anchor.geojson` |

		- 두 기능은 화면이 분리되어 있으므로 같은 이름을 써도 혼동되지 않는다.
		- IMDF 공식 스펙의 Anchor Feature는 `unit_id`(속한 Unit) 참조가 필요하다. 9항의 Anchor는 건물 외곽 모서리 등 unit 밖에 놓이는 경우가 많으므로 `anchor.geojson`으로 내보내지 않고 프로젝트 파일에만 남긴다.

10. Opening 선행 태깅과 '임시 폐쇄' (문 빌려주기)

	- **문제:** unit·footprint·level·venue 등은 **닫힌 폴리곤**이 필요한데, 실제 도면의 방은 벽에 문이 뚫려 있어 위상적으로 닫히지 않는다. 개구부만큼 벽 선이 끊겨 있으니 그 방과 복도가 하나로 이어진 영역이 된다.
	- **해법:** 문을 **임시로 닫아** 폴리곤을 완성한 뒤, 문 개체 자체는 opening으로 돌려보낸다.
	- 근거: Esri ArcGIS Indoors가 같은 문제를 `CLOSE_DOORS` 옵션으로 처리한다 — "type a Y or N to configure whether the... tool should treat the level's doors as **closed** when generating unit features from CAD polylines." 상세는 `01) Wiki/.../A-06-01) Indoor Map Overall/07) 도면의 방·문·창이 IMDF 좌표가 되는 기준.md` 5.3절.

	1) Opening 선행 태깅 강제
		1) 앱은 **opening을 다른 모든 property type보다 먼저 태깅하도록 강제**한다. opening 태깅이 끝나기 전에는 좌측 사이드바의 다른 property type 메뉴가 전부 비활성이다.
		2) 비활성 메뉴 클릭 시 안내: "opening을 먼저 태깅해야 합니다. 문을 먼저 확정해야 방 폴리곤을 닫을 수 있습니다."
		3) **완료 판정은 자동으로 할 수 없다.** 도면에 문이 몇 개인지 프로그램이 알 수 없기 때문이다. 따라서 opening 레이어에 **'opening 태깅 완료' 선언 버튼**을 둔다. 사용자가 이 버튼을 눌러야 다른 메뉴가 열린다.
		4) 완료 선언은 **되돌릴 수 있다.** 작업 도중 빠뜨린 문을 발견하면 opening 레이어로 돌아가 추가할 수 있고, 이때 기존에 저장한 다른 feature는 그대로 유지된다.
		5) 완료 선언 없이 opening을 하나도 만들지 않은 채 진행하는 것도 허용한다(문이 없는 도면). 단 경고를 한 번 띄운다.

	2) '함께 선택' — 문 빌려주기
		1) opening으로 이미 저장된 개체는, 다른 property type 레이어에서 **예외적으로 함께 선택할 수 있다.** 이는 명세 4-1)·6-1)의 소유권 배타 규칙에 대한 **유일한 예외**다.
		2) 함께 선택 시 4-1)의 경고창을 띄우지 않는다. 대신 해당 개체를 **점선 테두리 + 다른 색**으로 표시해 "빌려온 것"임을 시각적으로 구분한다.
		3) 빌려온 opening 개체는 상단바의 '그룹 해제' 대상이 아니다. 반납만 가능하다.
		4) 빌려줄 수 있는 대상은 **닫힌 폴리곤이 필요한 feature type에 한한다.**

		| feature type | geometry | 빌려주기 |
		|---|---|---|
		| unit | Polygon | ○ |
		| footprint | Polygon | ○ |
		| level | Polygon | ○ |
		| venue | Polygon | ○ |
		| fixture | MultiPolygon | ○ |
		| section | Polygon | ○ |
		| geofence | Polygon | ○ |
		| amenity | **Point** | ✗ — 점 하나라 닫을 폴리곤이 없다 |
		| opening | LineString | ✗ — 자기 자신 |
		| address · occupant | null | ✗ — geometry 없음 |
		| anchor | Point | ✗ |

		- **판정 기준을 규칙으로 고정한다:** geometry가 Polygon 또는 MultiPolygon인 type만 빌릴 수 있다. type을 추가할 때 표를 손으로 고칠 필요가 없다.

		5) **하나의 opening을 여러 feature가 동시에 빌릴 수 있다.** 방 A와 방 B 사이의 문은 양쪽 폴리곤을 모두 닫아야 하기 때문이다. 빌려주기는 소유권과 달리 배타적이지 않다.
		6) **대여는 opening → 타 type 한 방향뿐이다(2026-08-24 확정).** 벽이 소유하고 opening이 빌리는 반대 방향은 만들지 않는다. 문틀 선분처럼 opening이면서 벽이기도 한 개체가 있더라도, 최종적으로 추출하는 것은 **좌표뿐**이라 어느 쪽이 소유하든 결과가 같기 때문이다. 양방향 대여를 허용하면 순환 참조와 소유권 판정 복잡도만 늘어난다.

	3) 좌표만 넘기고 반납
		1) 빌려온 opening 개체는 해당 feature의 **좌표 계산에만 참여**한다. 문 LineString의 양 끝점이 폴리곤 링의 꼭짓점이 되고, 문 선분 자체가 링의 한 변이 되어 폴리곤이 닫힌다.
		2) **소유권은 이동하지 않는다.** 빌려온 개체는 여전히 opening 소유이며, opening 레이어에서 그대로 보인다.
		3) 따라서 다음이 성립한다.
			- 좌측 사이드바 진행률의 분자에 **중복 계산되지 않는다** (opening 몫으로 이미 세었다)
			- unit feature를 삭제해도 opening feature는 남는다
			- opening feature를 휴지통에 보내면, 그것을 빌린 모든 feature의 폴리곤이 열린다 → 경고 필요(10-4-3 참조)
		4) 우측 사이드바 feature 인스펙터에서 빌려온 개체는 별도 섹션으로 표시한다: `빌려온 opening (2)  opening-004, opening-011`.

	4) 검증
		1) 문 선분의 양 끝점이 벽 선분의 끝점과 실제로 만나야 폴리곤이 닫힌다. 눈으로 붙어 보여도 미세하게 벌어져 있으면 닫히지 않는다.
		2) 허용 오차를 두고 판정하며, 오차 안이면 스냅으로 붙인 것으로 간주한다. Esri의 대응 개념은 `Door Close Buffer` — "used to account for **poor CAD topology** — for example, line gaps between doors and walls."
		3) 빌린 뒤에도 링이 닫히지 않으면 저장 시 경고: "폴리곤이 닫히지 않았습니다. 빌려온 opening과 벽 사이에 {n}mm 간격이 있습니다." 어느 지점인지 캔버스에 표시한다.
		4) opening feature를 휴지통에 보낼 때, 그것을 빌린 feature가 있으면 경고: "이 opening을 {unit-012, unit-013}이 사용 중입니다. 삭제하면 해당 폴리곤이 열립니다."

	5) 내보내기
		1) `opening.geojson` — 빌려준 것과 무관하게 opening feature 전체가 정상 출력된다.
		2) `unit.geojson` 등 — 빌려온 opening의 끝점이 링 좌표에 포함된다. 단 **opening 개체가 unit의 구성원으로 기록되지는 않는다.** IMDF에 "이 unit이 저 opening을 빌렸다"를 기록하는 필드가 없기 때문이며, 그럴 필요도 없다 — 최종 산출물에는 닫힌 링 좌표만 남으면 된다.
		3) 즉 빌려주기는 **편집 시점의 개념**이고, 파일에는 그 흔적이 남지 않는다.
