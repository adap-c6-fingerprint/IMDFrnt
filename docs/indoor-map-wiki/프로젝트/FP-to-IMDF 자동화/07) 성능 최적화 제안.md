## 0. 요약

캔버스를 드래그할 때 멈추는 진짜 이유는 **개체를 몇 개 그리느냐가 아니라, 손가락이 1픽셀 움직일 때마다 앱이 도면 전체를 처음부터 다시 계산한다는 것**이다. 드래그 한 번에 초당 60번씩, 매번 다음이 통째로 다시 돌아간다.

1. 선택한 개체와 다른 모든 개체의 **겹침 검사**(`overlapHighlight`) — 개체 수의 제곱에 비례하는 계산
2. 개체 하나하나의 **표시 상태 재판정**(`renderState`) — 그 안에서 feature 목록을 매번 처음부터 훑는 탐색
3. 개체 하나하나의 **선·곡선을 화면 경로로 다시 만들기**(`swiftUIPath`, `translated`) — 매 프레임 새 메모리 할당

즉 무거움의 원인은 "레이어가 개체를 복사해 온다"기보다 **"매 프레임 전부 다시 만든다"**에 가깝다. 그래서 해법도 레이어 구조 하나가 아니라 ① 매 프레임 계산을 없애고(캐시), ② 다시 그릴 범위를 좁히고(분리·컬링), ③ 레이어를 목록이 아닌 규칙으로 두는 세 갈래다. 1·2단계만 해도 드래그는 되살아난다.

> **용어 먼저.**
> - **프레임**: 화면을 다시 그리는 한 번. 부드러우려면 1초에 60번, 즉 한 번에 16밀리초 안에 끝나야 한다. 개체 2,000개짜리 도면에서 한 프레임에 수백만 번 계산이 들어가면 이 예산을 몇십 배로 넘긴다.
> - **캐시**: 한 번 계산한 결과를 적어 두고, 재료가 바뀌지 않았으면 그 적어 둔 값을 그대로 쓰는 것. 매번 다시 계산하지 않는다.
> - **O(n²)(제곱 비례)**: 개체가 2배 늘면 계산은 4배, 10배 늘면 100배가 되는 계산. 개체 500개에서 멀쩡하던 것이 2,000개에서 16배 느려지는 이유다.

## 1. 사용자가 지목한 원인에 대한 확인

사용자가 지목한 것은 "type property 레이어가 생성될 때마다 모든 벡터 개체를 새로 가져온다"였다. 확인 결과는 반은 맞고 반은 다르다. **먼저 적어 두는 이유는, 이 차이에 따라 고칠 자리가 완전히 달라지기 때문이다.**

- **설계 문서에는 그렇게 적혀 있다.** `02) 아키텍쳐.md` 355줄 `EditorLayer`의 `var visibleObjectIDs: Set<VectorObjectID>` — "속성 필터 레이어는 부분집합, 나머지는 전체". 레이어마다 개체 id를 통째로 한 벌씩 들고 있으라는 설계다. 레이어를 10장 만들면 id 집합이 10벌 생긴다.
- **실제 코드에는 그 필드가 없다.** `Model/EditorLayer.swift`의 실제 필드는 `id`, `kind`, `isHidden`, `extraObjectIDs`(사용자가 필터 레이어에 손으로 더한 개체만)뿐이다. `Store/Stores.swift:110`의 `addPropertyTypeLayer`도 레이어 한 칸을 목록에 덧붙이고 활성 레이어를 바꾸는 것이 전부다.
- **다만 결과적으로 "전부 새로 가져오는" 동작은 있다.** 레이어를 만들면 활성 레이어가 바뀌고, 활성 레이어는 `renderState`(`App/AppEnvironment.swift:503`)에서 **모든 개체의 표시 여부를 정하는 1차 기준**이다. 그래서 레이어 하나를 만들 때마다 도면 전체가 다시 판정되고 다시 그려진다. 체감은 사용자가 말한 그대로다.
- **그런데 드래그가 멈추는 것은 이것과 별개다.** 레이어 생성은 클릭 한 번에 한 번이지만, 드래그는 1초에 수십 번이다. **같은 크기의 계산이라도 60배 자주 일어나면 그때만 멈춘다.** 아래 2장이 그 자리다.

**확인 필요:** `visibleObjectIDs` 조항은 코드에 구현되지 않았고, 아래 6장의 이유로 **구현하지 않는 편이 낫다**고 본다. `02) 아키텍쳐.md` 355줄에서 이 줄을 지워도 되는지 확인 부탁드립니다.

## 2. 드래그가 멈추는 자리 — 코드로 확인한 것

드래그 중 `CanvasView.dragGesture`는 매 프레임 `env.applyMove(...)`를 호출한다(`UI/CanvasView.swift:324`). 이것이 `@Published var transientOffsets`(`AppEnvironment.swift:608`)를 바꾸고, `@Published`가 바뀌면 **이 환경을 보고 있는 모든 화면이 다시 그려진다.** 그 뒤에 이어지는 것이 아래 넷이다.

### 2-1. 겹침 검사 — 가장 큰 원인

```swift
// AppEnvironment.swift:663
var overlapHighlight: OverlapDetector.Result {
    guard showOverlapHighlight, !selection.selected.isEmpty, let doc = document else { ... }
    return OverlapDetector.detect(selected: selection.selected,
                                  among: selectableObjects(in: doc), ...)
}
```

이것은 **저장된 값이 아니라 계산식**이다(Swift의 computed property). 캔버스가 `env.overlapHighlight`를 읽는 자리(`CanvasView.swift:195`)에서 **매 프레임 처음부터 전부 다시 계산된다.** 한 프레임에 일어나는 일을 풀면:

1. `selectableObjects(in: doc)`(`AppEnvironment.swift:847`)가 **모든 개체에 대해 `renderState`를 호출**한다.
2. `OverlapDetector.detect`(`Geometry/OverlapDetector.swift:26`)가 **모든 개체의 선분 목록과 경계 상자를 새로 만든다.** 곡선은 `lineSegments()`(`Model/Geometry.swift:101`)가 그때그때 잘게 쪼개므로(`CurveFlattener.subdivideCubic`), 개체 하나가 선분 수십~수백 개로 불어난다.
3. 그다음 선택 개체 × 나머지 개체 × 선분 × 선분으로 교차 검사를 돈다. 경계 상자로 먼저 걸러 내긴 하지만, 도면은 원래 개체들이 다닥다닥 붙어 있어 걸러지는 비율이 낮다.

개체 2,000개, 개체당 평균 선분 20개면 프레임당 선분 쌍 비교가 수백만 번이다. **16밀리초 예산으로는 불가능한 양이고, 이것 하나만으로 드래그가 멈춘다.**

덧붙여 이 기능은 지금 기본값이 켜짐(`showOverlapHighlight = true`)이고, `02) 아키텍쳐.md`가 이미 적어 둔 "알려진 한계"대로 **이동한 개체에는 어차피 어긋난 자리를 그린다**(겹침은 원본 좌표로 계산, 그림은 옮긴 좌표). 즉 지금은 **드래그 중에 비싸기만 하고 틀린 결과를 그리는 계산**이다.

### 2-2. 개체마다 표시 상태를 다시 판정 — 숨은 제곱 계산

```swift
// AppEnvironment.swift:503
func renderState(for object: VectorObject) -> ObjectRenderState {
    let ownerFeature = ownership.ownerOf(object.id)
    let ownerType = ownerFeature.flatMap { features.feature($0)?.featureType }
    ...
}
```

`features.feature(_:)`는 `features.first { $0.id == id }`(`Store/Stores.swift:43`), 즉 **feature 목록을 앞에서부터 하나씩 비교하는 탐색**이다. 개체 2,000개 × feature 300개면 프레임당 60만 번 비교가 여기서만 나온다. 게다가 `renderState`는 그리기 루프(`CanvasView.swift:149`)와 `selectableObjects`에서 **한 프레임에 두 번 이상** 호출된다.

### 2-3. 화면 경로를 매 프레임 새로 만들기

```swift
// CanvasView.swift:148-152
for o in doc.objects {
    let st = env.renderState(for: o)
    let g = env.displayGeometry(for: o)   // 이동량을 얹은 새 geometry를 통째로 복사
    let path = g.swiftUIPath              // 그 복사본으로 Path를 처음부터 다시 조립
```

`displayGeometry`(`AppEnvironment.swift:614`)는 `translated(by:)`로 **모든 점을 옮긴 새 구조체를 만든다**(`Model/Geometry.swift:84`). 이어서 `swiftUIPath`(`CanvasView.swift:5`)가 그 점들을 다시 훑어 `Path`를 조립한다. **개체 2,000개면 프레임마다 메모리 할당이 수천 번**이다. 실제로는 **옮긴 개체 몇 개 말고는 지난 프레임과 완전히 같은 그림**인데도 그렇다.

여기에 하위 기본 레이어(고스트)가 켜져 있으면 `for o in doc.objects`가 한 번 더 돈다(`CanvasView.swift:137`). 그리기 비용이 그대로 두 배다.

### 2-4. 캔버스 말고 다른 화면까지 다시 그리기

`transientOffsets`는 `AppEnvironment` 하나에 `@Published`로 붙어 있고, 좌·우 사이드바가 모두 `@EnvironmentObject var env: AppEnvironment`로 그 환경을 본다(`UI/LeftSidebar.swift:5`, `UI/RightSidebar.swift:5`). **개체를 1픽셀 옮길 때마다 사이드바의 feature 목록·진행률·좌표 표까지 다시 계산된다.** 드래그와 아무 상관이 없는 화면들이다.

여기에 `openRingGaps`(`AppEnvironment.swift:575`)도 매 프레임 다시 계산되는 계산식이라, 펼쳐 둔 feature가 있으면 링 닫힘 검사까지 프레임마다 얹힌다.

## 3. 제안 — 효과가 큰 순서

각 제안마다 **어느 파일의 어느 함수를 어떻게 고치는지**를 함께 적는다. 코드 조각은 그대로 붙여 넣는 완성본이 아니라 **바꿀 자리와 방향을 정확히 가리키는 뼈대**다. 줄 번호는 2026-08-26 기준이라, 앞 제안을 먼저 적용하면 뒤 제안의 줄 번호는 밀린다 — 함수 이름으로 찾는 편이 안전하다.

### 공통 규칙 — 캐시를 넣기 전에 정해 둘 것

아래 제안 대부분은 "미리 계산해 두고 재료가 바뀔 때만 다시 계산한다"이다. 이때 **다시 계산해야 하는데 안 하는 것**(옛 그림이 남는다)이 가장 찾기 어려운 버그다. 그래서 다음 두 가지를 규칙으로 못 박고 시작한다.

1. **무효화(다시 계산해야 한다는 표시)는 한 곳에서만 한다.** 캐시를 지우는 코드를 여기저기 흩으면 새 기능이 들어올 때마다 한 군데씩 빠진다. `AppEnvironment`의 `@Published` 속성에 `didSet`을 달아, **상태가 바뀌는 그 자리에서 자동으로** 표시되게 한다.

```swift
// App/AppEnvironment.swift — 지금
@Published var selection = SelectionStore()

// 바꾼 뒤
@Published var selection = SelectionStore() {
    didSet { if selection != oldValue { invalidateRenderStates(); refreshOverlap() } }
}
// 선택이 바뀌는 경로는 클릭·드래그 선택·전체 해제·실행취소 복원 등 여러 곳인데,
// 그 경로를 하나하나 찾아 캐시를 지우는 대신 값이 바뀌는 자리 한 곳에서 처리한다.
```

2. **캐시된 값과 직접 계산한 값이 같은지 `--selftest`가 검사한다.** 캐시를 넣은 뒤 "옛날 방식으로 계산한 결과"와 "캐시가 준 결과"를 비교하는 항목을 넣으면, 무효화를 빠뜨렸을 때 화면이 아니라 시험에서 먼저 걸린다.

### 제안 1. 드래그 중에는 겹침 검사를 하지 않는다 (즉효, 반나절)

**고칠 파일**: `App/AppEnvironment.swift`(`overlapHighlight`, 661~673줄 부근), `UI/CanvasView.swift`(195줄 부근)

#### 1-1. 계산식을 저장값으로 바꾼다

```swift
// App/AppEnvironment.swift — 지금 (매 프레임 전부 다시 계산된다)
var overlapHighlight: OverlapDetector.Result {
    guard showOverlapHighlight, !selection.selected.isEmpty, let doc = document else {
        return OverlapDetector.Result()
    }
    return OverlapDetector.detect(selected: selection.selected,
                                  among: selectableObjects(in: doc),
                                  segmentation: segmentation,
                                  tolerance: overlapTolerance)
}

// 바꾼 뒤 — 저장해 두고, 재료가 바뀔 때만 다시 채운다
@Published private(set) var overlapHighlight = OverlapDetector.Result()

func refreshOverlap() {
    guard showOverlapHighlight, !selection.selected.isEmpty, let doc = document else {
        if !overlapHighlight.isEmpty { overlapHighlight = OverlapDetector.Result() }
        return
    }
    overlapHighlight = OverlapDetector.detect(selected: selection.selected,
                                              among: selectableObjects(in: doc),
                                              segmentation: segmentation,
                                              tolerance: overlapTolerance)
}
// 이름을 그대로 두는 것이 중요하다. `CanvasView`·`SelectionToolbar`·`--selftest`가
// 이미 `overlapHighlight`를 읽고 있어, 이름을 바꾸면 고칠 자리가 불필요하게 늘어난다.
```

`refreshOverlap()`을 부르는 자리는 **재료가 바뀌는 네 곳**뿐이다. 전부 `didSet`으로 묶는다.

| 재료 | 지금 선언 | 붙일 것 |
| --- | --- | --- |
| 선택 | `@Published var selection` | `didSet { refreshOverlap() }` |
| 선분화 | `@Published var segmentation` | `didSet { refreshOverlap() }` |
| 표시 토글 | `@Published var showOverlapHighlight` | `didSet { refreshOverlap() }` |
| 문서 | `@Published var document`(이미 `didSet` 있음) | 그 안에 `refreshOverlap()` 한 줄 |

**드래그 중에는 이 넷 중 무엇도 바뀌지 않는다.** 그래서 프레임당 수백만 번 비교가 저절로 0이 된다. 이것이 이 제안의 핵심이고, 별도의 "드래그 중 끄기" 코드가 없어도 목적이 달성된다.

#### 1-2. 이동 중에는 그리지 않는다

겹침은 원본 좌표로 계산하는데 개체는 옮긴 자리에 그려지므로, 이동 중 겹침 표시는 어긋난 자리를 가리킨다(`06) 확인 필요.md` A12).

```swift
// `beginMove()`에서 true, `CanvasView.dragGesture`의 `onEnded`에서 false.

// UI/CanvasView.swift — 195줄
let overlap = env.overlapHighlight
if !overlap.isEmpty {

// 바꾼 뒤
let overlap = env.isMovingObjects ? OverlapDetector.Result() : env.overlapHighlight
if !overlap.isEmpty {
```

#### 1-3. 검증

- `--selftest`: 선택을 바꾼 뒤 `env.overlapHighlight`가 즉시 갱신되는지, 선택을 비우면 비는지, `showOverlapHighlight = false`면 비는지 3항목.
- 눈 확인: 개체를 골랐을 때 분홍 윤곽이 종전과 똑같이 뜨는지.

### 제안 2. 개체별 파생 데이터를 한 번만 만들어 들고 있는다 (핵심, 1~2일)

**새로 만들 파일**: `App/RenderCache.swift`
**고칠 파일**: `UI/CanvasView.swift`(`canvas(doc:viewport:)`), `Geometry/HitTester.swift`, `Geometry/OverlapDetector.swift`

#### 2-1. 캐시 그릇

```swift
// App/RenderCache.swift (신규)
import SwiftUI

/// 개체 하나에서 파생되는, 매 프레임 다시 만들 이유가 없는 것들.
struct ObjectRenderCache {
    let path: Path
    let segments: [LineSegment]
    let box: CGRect
}

@MainActor
final class RenderCacheStore {
    private var entries: [VectorObjectID: ObjectRenderCache] = [:]

    func entry(for object: VectorObject, segmentation: SegmentationStore) -> ObjectRenderCache {
        if let hit = entries[object.id] { return hit }
        let geo = segmentation.effectiveGeometry(for: object.id, fallback: object.geometry)
        let made = ObjectRenderCache(path: geo.swiftUIPath,
                                     segments: geo.lineSegments(),
                                     box: geo.boundingBox)
        entries[object.id] = made
        return made
    }

    func invalidate(_ id: VectorObjectID) { entries.removeValue(forKey: id) }
    func invalidateAll() { entries.removeAll() }
}
```

#### 3-3. feature 조회를 한 번에 찾게 바꾼다

```swift
// Store/Stores.swift — 지금 (43줄): 목록을 앞에서부터 훑는다
func feature(_ id: FeatureGroupID) -> FeatureGroup? {
    features.first { $0.id == id }
}

// 바꾼 뒤 — 배열은 그대로 두고 위치 사전을 옆에 둔다
struct FeatureStore: Equatable, Codable {
    private(set) var features: [FeatureGroup] = []
    private var indexByID: [FeatureGroupID: Int] = [:]

    enum CodingKeys: String, CodingKey { case features }
    // 사전은 저장하지 않는다 — 배열에서 언제든 다시 만들 수 있고,
    // 파일에 넣으면 옛 파일과 새 파일의 형식이 갈린다.

    init() {}
    init(from decoder: Decoder) throws {
        let c = try decoder.container(keyedBy: CodingKeys.self)
        features = try c.decode([FeatureGroup].self, forKey: .features)
        rebuildIndex()
    }

    static func == (l: FeatureStore, r: FeatureStore) -> Bool { l.features == r.features }
    // 사전은 배열에서 파생된 값이라 비교 대상이 아니다. 넣으면 실행취소의
    // "바뀐 게 없다" 판정(`perform`)이 엉뚱하게 달라질 수 있다.

    func feature(_ id: FeatureGroupID) -> FeatureGroup? {
        guard let i = indexByID[id], features.indices.contains(i) else { return nil }
        return features[i]
    }

    private mutating func rebuildIndex() {
        indexByID = Dictionary(uniqueKeysWithValues: features.enumerated().map { ($1.id, $0) })
    }

    mutating func insert(_ f: FeatureGroup) { features.append(f); indexByID[f.id] = features.count - 1 }
    mutating func remove(_ id: FeatureGroupID) { features.removeAll { $0.id == id }; rebuildIndex() }
    mutating func update(_ id: FeatureGroupID, _ body: (inout FeatureGroup) -> Void) {
        guard let i = indexByID[id] else { return }
        body(&features[i])
    }
    // `update`는 자리를 바꾸지 않으므로 사전을 다시 만들 필요가 없다.
    // `remove`만 뒤 항목의 자리를 당기므로 다시 만든다.
}
```

`ownership.ownerOf`는 이미 사전이라 손대지 않는다.

```swift
// 화면 네 모서리를 도면 좌표로 옮겨 감싸는 사각형을 만든다.
// `toLocal`이 이미 회전까지 역변환하므로, 네 점을 다 변환한 뒤 min/max를 취하면
// 90° 회전 상태에서도 정확하다.
private func visibleDocRect(viewport: CGSize) -> CGRect {
    let corners = [CGPoint(x: 0, y: 0), CGPoint(x: viewport.width, y: 0),
                   CGPoint(x: 0, y: viewport.height),
                   CGPoint(x: viewport.width, y: viewport.height)].map { toLocal($0) }
    let xs = corners.map(\.x), ys = corners.map(\.y)
    return CGRect(x: xs.min()!, y: ys.min()!,
                  width: xs.max()! - xs.min()!, height: ys.max()! - ys.min()!)
}
```

- **`EditorLayer`는 지금 구조를 유지한다.** `visibleObjectIDs`를 넣지 않는다. 넣으면 레이어 수만큼 개체 id 집합이 생기고, 개체 하나가 태깅될 때마다 전부 고쳐야 한다 — 한 벌이라도 빠지면 레이어마다 보이는 것이 달라지는 버그가 된다.
- **문서 수정**: `02) 아키텍쳐.md` 355줄의 `var visibleObjectIDs: Set<VectorObjectID>` 줄을 지우고, 그 자리에 "표시 여부는 `renderState`가 규칙으로 판정한다(개체 목록을 복사하지 않는다)"를 적는다.
- **속성 필터 레이어만 색인을 둔다.** 복사가 아니라 조회용 색인이다.

```swift

objectsByAttributeKey = Dictionary(grouping: doc.objects, by: { $0.style.attributeKey })
    .mapValues { $0.map(\.id) }
// `addAttributeFilterLayer`가 후보를 즉시 얻는다. 지금은 레이어를 열 때마다
// 모든 개체의 `attributeKey`를 다시 비교한다.
```

### 제안 7. 레이어 생성·개체 추가가 무거운 것 — 실행취소 스냅샷 (측정 후 판단)

**고칠 파일**: `App/AppEnvironment.swift`(`perform`, 888줄), `Store/UndoStack.swift`

```swift
// 지금 — 상태 전체를 복사하고, 작업 뒤 전체를 다시 비교한다
func perform(_ name: String, coalescingKey: String? = nil, _ body: () -> Void) {
    let before = snapshot
    undoStack.record(name, coalescingKey: coalescingKey, before: before)
    body()
    if snapshot == before, undoStack.undoName == name { undoStack.discardLast() }
}
```

`EditorSnapshot`은 12개 스토어를 담은 구조체이고, `snapshot == before`는 그 전부를 깊이 비교한다. feature가 수백 개면 클릭 한 번에 이 비교가 통째로 돈다.

**바꾸는 방향(측정에서 무겁게 나올 때만)**: 비교를 없애고, 바뀌었는지를 작업 쪽이 직접 알려 준다.

```swift
@discardableResult
func perform(_ name: String, coalescingKey: String? = nil, _ body: () -> Bool) -> Bool {
    let before = snapshot
    undoStack.record(name, coalescingKey: coalescingKey, before: before)
    if !body() { undoStack.discardLast(); return false }
    return true
}
// 호출부는 "실제로 바꿨는가"를 반환한다. 예: `layers.activate(id)`는 이미 Bool을 준다.
```

**위험**: 호출부가 `true`를 잘못 반환하면 아무 일도 안 하는 실행취소 칸이 쌓이고, `false`를 잘못 반환하면 **cmd+z가 먹지 않는다**(`UndoStack.swift` 26~27줄이 경고하는 바로 그 종류의 버그다). 그래서 이 제안은 **7순위이며, 측정에서 실제로 무겁게 나올 때만** 손댄다. Swift의 배열·사전은 복사할 때 실제 데이터를 바로 복제하지 않으므로(값이 바뀔 때만 복제), 복사보다 **비교**가 더 비쌀 가능성이 높다 — 측정이 그 둘을 구분해 줄 것이다.

**제안 1~6을 전부 적용했다. 제안 7은 문서가 정한 규칙대로 측정한 뒤 적용하지 않기로 했다.**

### 측정값 (release 빌드, 개체 2,000개 합성 도면, `--selftest`)

| 항목 | 결과 |
| --- | --- |
| 표시 상태 사전 | 최초 5.2 ms → **이후 0.0000 ms/프레임**(캐시) |
| Path·선분 만들기 | 최초 1.9 ms → 이후 0.4 ms/프레임(조회만) |

### 새로 들어간 회귀 시험 (`--selftest`, 17항목)

캐시는 "다시 계산해야 하는데 안 하는 것"이 가장 찾기 어려운 버그다. 그래서 **캐시가 준 값과 직접 계산한 값이 같은지**를 검사한다.

- 표시 상태 사전 = 직접 계산 / 선택이 바뀌면 즉시 갱신
- 파생 데이터 = 직접 계산 / 선분화하면 그 개체의 캐시만 다시 만들어짐
- 저장해 둔 겹침 = 직접 계산 / 선택이 비면 겹침도 비워짐
- 격자로 좁힌 클릭 판정 = 전수 검사 / 옮긴 개체는 격자 밖이어도 후보에 남음
- 속성 색인 = 도면 전체 비교
- 이동량은 별도 객체가 보유 / **좌표 추출은 이동을 보지 않음**(명세 2-3) / 드래그 종료 시 상태 해제 / 원위치
- 개체 2,000개 프레임 비용 3항목 + 스냅샷 비용 1항목

**GUI는 여전히 눈 확인이 필요하다**(`06) 확인 필요.md` C14). 특히 ① 실도면 드래그가 부드러운지 ② 확대한 상태에서 화면 밖 개체가 잘려 보이지 않는지(컬링 경계) ③ 선분화 직후 그림이 바로 바뀌는지.

## 5. 검증 방법

`--selftest`는 GUI 조작을 검증하지 못한다(`06) 확인 필요.md` C절). 성능은 특히 그렇다. 그래서 **숫자로 확인할 수 있는 기준을 먼저 정해 두고** 고친다.

- **측정용 도면 고정**: 실제 도면 하나를 기준 샘플로 정한다(개체 수를 문서에 적어 둔다). 개체 수가 다르면 앞뒤 비교가 의미가 없다.
- **프레임 시간 측정**: 드래그 중 한 프레임에 걸린 시간을 로그로 남기는 개발용 스위치를 둔다. 목표는 **16밀리초 이하**, 최소한 **33밀리초 이하**(초당 30프레임)다.
- **계산 횟수 세기**: `renderState`·`lineSegments`·`OverlapDetector.detect` 호출 횟수를 세는 카운터를 붙여, 드래그 100프레임 동안 호출이 **0에 수렴하는지** 확인한다. 시간보다 이 숫자가 원인을 정확히 가리킨다.
- **Instruments의 Time Profiler**로 실제 어디에 시간이 몰리는지 확인한다. 위 분석은 코드 읽기에 근거한 것이라, 실측과 다를 수 있다.
- **회귀 시험**: 캐시를 넣은 뒤 ① 선분화한 개체의 그림이 즉시 바뀌는지 ② 이동 후 클릭 판정이 옮긴 자리에서 맞는지 ③ 좌표 추출·내보내기가 여전히 **원본 좌표**를 쓰는지(명세 2-3의 핵심 규칙)를 `--selftest`에 넣는다.

## 7. 미해결 질문

1. **드래그 중 겹침 표시를 아예 끌지, 드래그가 끝난 뒤 다시 그릴지.** 제안 1은 후자를 전제로 썼다. 이동 중에도 겹침이 보여야 한다면 겹침 계산을 이동 좌표 기준으로 고치는 별도 작업이 필요하다(`06) 확인 필요.md` A12와 같은 사안).
2. **기준 도면의 실제 개체 수.** 위 추정치(2,000개)는 가정이다. 실제 도면의 개체 수와 곡선 비율에 따라 우선순위가 달라질 수 있다.
3. **하위 기본 레이어(고스트)의 기본 표시 여부.** 켜져 있으면 그리기 비용이 두 배다. 기본값을 꺼짐으로 두고 필요할 때 켜는 방식이 성능에는 유리한데, 원위치 확인이라는 목적과 충돌한다.
4. **제안 7(실행취소 스냅샷)을 이번 범위에 넣을지.** 실행취소는 이미 검증된 기능이라 손대면 회귀 위험이 있다. 측정 결과 무겁지 않으면 건드리지 않는 편이 낫다.
