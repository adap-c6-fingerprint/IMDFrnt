## 0. 설계 전제

- **플랫폼**: macOS, SwiftUI 단일 앱 타깃. 구버전에서 엔진/UI 패키지를 분리했다가 실제로는 단일 타깃으로 굴러간 전례가 있으므로(구버전 문서 7절 "⚠️"), 처음부터 단일 타깃 + 폴더(그룹) 분리로 간다.
- **입력은 SVG 하나**. DWG/DXF 전처리 단계는 새버전 명세에 없다.
- **개체는 절대 삭제되지 않는다**(명세 2항). 따라서 문서 모델은 "불변(immutable) 개체 목록 + 그 위에 얹히는 가변 상태(선택·이동·소속)"로 나눈다. 이 분리가 아키텍처 전체의 뼈대다.
- **개체 하나는 전 레이어를 통틀어 최대 하나의 feature 그룹에만 속한다**(명세 4-1, 6-1). 이 전역 유일성을 지키는 단일 진실 공급원이 `OwnershipRegistry`다.
- **단 하나의 예외가 있다 — opening 빌려주기**(명세 10항). 문이 뚫려 있으면 방 폴리곤이 닫히지 않으므로, opening으로 저장된 개체를 unit 등이 **빌려서 링을 닫는다.** 소유권은 opening에 그대로 있고 좌표만 빌려준다. 소유(exclusive)와 대여(non-exclusive)를 **다른 자료구조로 분리**하는 것이 이 예외를 안전하게 다루는 방법이다.
- **좌표는 Anchor가 찍히기 전까지 위경도가 없다**(명세 7-3-6). 그래서 "SVG 로컬 좌표"와 "위경도"를 타입 수준에서 구분한다(`LocalPoint` / `GeoPoint`).

### 0.1 확정 사항 (2026-08-24, Sano 검토 반영)

초안의 미해결 항목 5건이 모두 결론에 도달했다. 아래는 그 결론과, 그로 인해 설계가 바뀐 지점이다.

**1. SVG 파서 — 자체 구현으로 확정.**
SVGKit은 macOS 지원·유지보수가 불안정하고, 명세가 요구하는 "개체별 RGB·두께·점선 속성 비교"(명세 2항)를 위해 **원본 스타일 값에 그대로 접근**해야 한다. 렌더링만 해주는 라이브러리로는 부족하다. → `XMLParser` + 자체 path-data 파서.

**2. 곡선 선분화 — 수동 버튼으로 확정, 기능 범위 확대.**
자동 실행은 없다. 개체 선택 상단바의 '선분화' 버튼을 눌러야 실행되며, 명세 8-4)·3-3)이 이번에 확정된 아래 요구사항으로 갱신됐다.

- 버튼 클릭 시 곡률에 맞춰 자동 분할하되, 결과는 **하나로 이어진 폴리라인이 아니라 개별 선분들**이다.
- 각 선분은 곡률 지점에서 **반드시 만나야** 하고(끝점이 벌어지면 안 됨), 만나는 지점을 벗어나 **교차해서는 안 된다**.
- **선분화는 실행 취소 가능하다.** 원본 곡선 개체로 되돌릴 수 있어야 한다.
- 좌측 사이드바에 **'곡선 개체만 따로 보기'** 버튼이 추가된다. 곡선이 아닌 개체는 75% opacity, 이미 선분화된 곡선도 함께 표시. X 버튼으로 닫기.
- 그 창 안에서 곡선 개체를 개별 선택해 선분화할 수 있고, **'선분화된 곡선 개체만 보기'** 토글을 켜면 모든 곡선이 50% opacity, 선분화된 것만 100% opacity로 표시된다. 이때 선택 단위는 개별 선분이 아니라 **선분화 이전의 곡선 개체 단위**이며, 선택 상태에서 '선분화 해제'가 가능하다.

→ 설계 영향이 크다. "선분화 해제"와 "곡선 개체 단위 선택"이 가능하려면 선분화가 **원본 개체를 파괴적으로 대체해서는 안 된다.** 원본 `VectorObject`는 그대로 두고, 선분화 결과를 `originalObjectID → [LineSegment]` 파생 상태로 따로 보관한다(`SegmentationStore`). 이는 "개체는 삭제되지 않는다"는 명세 2항의 원칙과도 일관된다.

**3. 진행률 분모 — SVG 전체 개체 수로 확정. type별 진행률은 만들지 않는다.**
어떤 개체를 어떤 property type으로 편입시킬지는 사용자가 결정하므로 type별 분모를 정의할 수 없다. → 초안이 "부가 표시"로 뒀던 type별 진행률을 **삭제**하고, 좌측 사이드바 각 메뉴에는 진행률이 아닌 **저장된 feature 개수**만 배지로 표시한다.

**4. Feature id — RFC 4122 version 4 UUID로 확정 (추정 아님, 공식 스펙 MUST).**
OGC IMDF 1.0.0 Reference 원문: "Feature IDs **MUST** be a globally unique, RFC 4122 compliant **version 4** UUID". 함께 확인된 두 제약이 설계를 바꾼다.

- "MUST be retained... across distinct deliveries" — **한 번 발급한 UUID는 재내보내기 때도 유지**되어야 한다. 초안의 `IDAssigner`가 내보내기 때마다 새로 발급하는 구조였는데, 이는 스펙 위반이다. → 발급된 UUID를 `ProjectFile`에 영속 저장한다.
- "MUST NOT be re-assigned to another Feature of any type" — 휴지통에 간 feature의 UUID를 다른 feature가 물려받아서는 안 된다. → `IDAssigner`가 폐기 UUID 목록을 함께 보관한다.

**5. Anchor — 전용 화면으로 분리하고 최소 3쌍으로 확정.**
초안 검토 과정에서 한 차례 용어를 "기준점(컨트롤 포인트)"으로 바꿨다가 **되돌렸다.** 바꾼 이유는 좌측 사이드바의 `anchor` property type 메뉴와 이름이 겹친다는 것이었는데, 사용자 설계에서는 원래 그 둘이 같은 개념이었다 — Anchor가 곧 모든 좌표의 기준점이다.

대신 **화면을 분리**해서 충돌을 해소했다. 명세 9항이 이번에 신설됐다.

- Anchor 지정은 property type 작업과 성격이 달라 **전용 전체화면**에서 한다. 진입점은 좌측 사이드바 최상단(property type 목록 위, 구분선 사이).
- 좌우 분할 — 왼쪽 도면(SVG 캔버스), 오른쪽 지도(MapKit 위성 뷰). 도면에서 클릭 → 지도에서 같은 지점 클릭 → 한 쌍 완성.
- **위경도 직접 입력이 동등한 주 경로다.** 국내 대상 건물의 위성 해상도가 모서리를 찍을 만큼 안 나올 수 있고, 측량 성과·지적도 좌표를 이미 갖고 있는 경우가 흔하다.
- **2쌍이 모이면 도면을 지도 위에 반투명 오버레이**해 정합을 눈으로 확인할 수 있게 한다. 이건 미리보기 전용이라 상사 변환(자유도 4, 2쌍)으로 계산하고, 좌표 확정·내보내기에는 쓰지 않는다.
- **최소 3쌍(어파인) 요구, 4쌍 이상 권장.** 전용 화면이 생겨 클릭 부담이 낮아졌으므로 어파인 기준을 적용한다. 3쌍 정확히면 잔차가 항상 0이라 오지정 검출이 불가능하므로, 잔차 열을 0으로 표시하지 않고 `판정 불가 (Anchor 4쌍 이상 필요)`로 표시한다.

두 Anchor의 역할 구분:

| | Anchor 지정 화면 (명세 9항) | 사이드바 `anchor` 메뉴 (명세 3항) |
|---|---|---|
| 목적 | 도면↔지도 대응 쌍으로 변환식 산출 | unit에 속한 IMDF Anchor Feature 생성 |
| 좌표 | 사용자가 직접 지정 | 변환식으로 자동 계산, read-only |
| 개수 | 3~5개 | 주소·입주자 수만큼 |
| 산출물 | 프로젝트 파일 (변환식의 입력) | `anchor.geojson` |

IMDF 공식 스펙의 Anchor Feature는 `unit_id` 참조가 필요한데, 9항의 Anchor는 건물 외곽 모서리 등 unit 밖에 놓이는 경우가 많다. 그래서 **9항 Anchor는 `anchor.geojson`으로 내보내지 않고 프로젝트 파일에만 남긴다.**

**6. Opening 선행 태깅과 '문 빌려주기' — 소유권 배타 규칙의 유일한 예외.**
unit·footprint·level·venue는 닫힌 폴리곤이 필요한데, 실제 도면의 방은 벽에 문이 뚫려 있어 위상적으로 닫히지 않는다. 명세 10항이 이번에 신설됐다.

- **opening을 다른 모든 property type보다 먼저 태깅하도록 강제한다.** 완료 판정은 자동으로 할 수 없으므로(도면에 문이 몇 개인지 프로그램은 모른다) **'opening 태깅 완료' 선언 버튼**을 둔다. 되돌릴 수 있다.
- opening으로 저장된 개체는 다른 레이어에서 **예외적으로 함께 선택**할 수 있다. 문 선분이 링의 한 변이 되어 폴리곤이 닫힌다.
- **소유권은 이동하지 않는다.** 좌표만 빌려주고 개체는 opening에 남는다. 진행률 분자에도 중복 계산되지 않는다.
- **하나의 opening을 여러 feature가 동시에 빌릴 수 있다.** 방 A와 방 B 사이의 문은 양쪽을 모두 닫아야 하기 때문이다.

→ 설계 영향이 크다. 소유(배타)와 대여(비배타)를 **같은 자료구조에 섞으면 배타성 검사가 무너지므로**, `OwnershipRegistry`와 별개로 `BorrowRegistry`를 둔다. 후자는 값이 `Set<FeatureGroupID>`라 다중 대여를 표현한다. 이 구분이 무너지면 opening이 unit에 흡수되어 `opening.geojson`에서 사라진다.

이 패턴은 이 프로젝트의 발명이 아니다. Esri ArcGIS Indoors가 같은 문제를 `CLOSE_DOORS` 옵션으로 처리한다 — "treat the level's doors as **closed** when generating unit features from CAD polylines". 다만 Esri는 "닫고 → 폴리곤화 → 다시 열어 Opening 추출" 순서인 반면, 이 앱은 사람이 직접 태깅하므로 **"opening 먼저 확정 → 빌려서 닫기"로 순서가 뒤집혀 있다.** 결과는 같다.

**7. 캔버스 배경 밝게/어둡게 전환.**
도면 배경을 사용자가 전환할 수 있게 한다. CAD SVG는 대개 검은 선이라 밝은 배경이 기본이지만, 흰 선으로 그려진 도면이나 장시간 작업에는 어두운 배경이 낫다.

→ 단순 색 교체로는 부족하다. **검은 선 도면을 어두운 배경에서 열면 아무것도 보이지 않는다.** 그래서 `CanvasBackground.resolve(_:)`가 선 색의 상대 휘도를 배경 휘도와 비교해, 너무 가까우면(차이 0.28 미만) 반전시킨다. SVG 원본 색은 보존하고 표시할 때만 반전하므로 '같은 속성 모아보기'의 비교 기준에는 영향이 없다.

### 0.2 남은 미해결 항목

- **CSS `<style>` 블록 지원 범위**: `StyleResolver`가 인라인 `style` 속성과 프레젠테이션 속성만 처리할지, SVG 내부 CSS 셀렉터까지 해석할지 미정.
- **`fn+shift+z` 키 반복 처리**: 문자키 `z`를 길게 누르면 auto-repeat이 발생한다. 유지 구간 판정에서 반복 이벤트를 걸러야 한다(2.8절).
- **선분화 tolerance 기본값**: 곡률 대비 몇 개의 선분으로 쪼갤지의 기본값이 미정. 설정으로 노출하되 초기값 결정 필요.
- **`category` 허용값 전수 대조**: `CategoryCatalog.json`의 값이 IMDF 스펙 CATEGORY 열거형과 전량 대조되지 않았다.
- **지오레퍼런싱 정확도 목표치**: Apple Indoor Maps Program이 요구하는 허용 오차(m 단위)가 공식 문서에서 확인되지 않았다. 잔차 경고 임계값을 정할 근거가 아직 없다.
- **`RingCloser` 허용 오차 기본값**: Esri `Door Close Buffer`의 기본값과 실무 권장 범위가 도구 참조 페이지에 수치로 명시되어 있지 않다(위키 `07)` 문서의 미해결 질문과 동일). 폴리곤화 일반 기준인 ArcGIS Indoors의 xy tolerance 기본 1mm가 출발점이 될 수 있으나 문-벽 간격은 그보다 클 것으로 보인다.
- **`section`·`geofence`의 properties 전수 대조**: 두 type을 메뉴에 추가했으나(2026-08-24), `src11`이 section의 properties를 "`category`, `name`, `alt_name`, `display_point` 등"까지만 확인해 뒀다. OGC 개별 페이지 재조회로 전수 확인 필요. `GEOFENCE-CATEGORY` 8종 열거값도 미확보.

#### `SampleFloorplan.swift` — 자체점검 전용 (디버깅 12번, 2026-08-25)
테스트 도면 SVG를 문자열로 실행 파일에 직접 넣은 것. SPM 리소스 번들 경로에 의존하지 않아 `swift run`과 `.app` 양쪽에서 같게 동작한다.

- `openSample()` 위에 이 사실을 주석으로 못박아 뒀다. 안 그러면 다음에 보는 사람이 "아무도 안 부르는 코드"로 알고 지워 자체점검을 깨뜨린다
- 자체점검이 **앱 시작 시 `document == nil`** 을 확인한다 — 샘플이 자동으로 적재되는 회귀를 막는 장치다

#### `SVGParser.swift`
`XMLParser`로 SVG 트리를 순회하며 **그리기 요소(`path`, `rect`, `circle`, `ellipse`, `line`, `polyline`, `polygon`)를 개별 `VectorObject`로 평탄화**한다. `<g>`는 좌표계 누적(transform)과 스타일 상속에만 쓰고, 개체로 만들지 않는다 — 명세의 "그룹화"는 사용자가 직접 하는 것이지 SVG의 `<g>`가 아니기 때문이다.
- `func parse(data: Data) throws -> [VectorObject]`
- `private func makeObject(element:attributes:) -> VectorObject?`
- `private func shapeToPath(element:attributes:) -> PathGeometry` — `rect`/`circle` 등 기본 도형을 path로 통일 변환
- `viewBox`/`width`/`height`를 읽어 `DrawingDocument.canvasSize`로 넘김

#### `PathDataParser.swift`
`d="M10 10 C ..."` 문자열을 세그먼트 배열로 파싱. 20종 명령(`MmLlHhVvCcSsQqTtAaZz`) 전부 처리하고, 상대좌표·연속 명령·암시적 `L` 반복을 정규화한다. **`A`(호)는 여기서 곡선 세그먼트로 남겨두고, 직선화는 `CurveFlattener`가 담당**한다.
- `func parse(_ d: String) throws -> [Subpath]`
- `private func normalizeToAbsolute(...)`
- `private func arcToCubic(...) -> [CubicSegment]` — SVG 호 파라미터를 3차 베지어로 환산

#### `StyleResolver.swift`
"같은 속성의 벡터만 모아보기"(명세 2항)의 근거가 되는 파일. `style` 속성·프레젠테이션 속성·부모 상속을 합쳐 최종 스타일을 산출한다. CSS `<style>` 블록까지는 1차 범위 밖(확인 필요).
- `func resolve(attributes:inherited:) -> VectorStyle`
- `func attributeKey(for style: VectorStyle) -> StyleKey` — RGB·두께·점선 패턴을 묶은 해시 키. 이 키가 같은 개체끼리 한 레이어로 모인다

#### `TransformStack.swift`
`transform="translate(...) rotate(...)"` 누적 행렬 관리.
- `func push(_ transform: String)` / `func pop()`
- `var current: CGAffineTransform`
- `func flatten(_ path: PathGeometry) -> PathGeometry` — 파싱 시점에 좌표를 최종 좌표계로 굽는다(런타임 변환 비용 제거)

#### `SVGImportError.swift`

### 2.3 Model/

#### `VectorObject.swift`
**불변**. SVG에서 읽은 개체 하나. 삭제 불가라는 명세 2항이 여기 반영된다 — 어떤 코드도 이 배열에서 원소를 빼지 않는다.
- `let id: VectorObjectID` (UUID)
- `let geometry: PathGeometry` — 원위치 좌표(하위 기본 레이어가 이 값을 그린다)
- `let style: VectorStyle`
- `let sourceElement: String` — 디버깅용 원본 태그명
- `var boundingBox: CGRect { get }`
- `var isCurved: Bool { get }` — 선분화 버튼 활성화 조건
- `var twinKey: String { get }` — "똑같이 생긴 개체" 판정 키(디버깅 6번, 2026-08-25). **위치를 보지 않는다** — bounding box 원점으로 평행이동한 좌표(0.01 반올림) + `style.attributeKey` + 요소 종류를 이어 붙인다. 보조 개체는 같은 모양이 위치만 달리해 수십 개씩 흩어져 있는 게 특징이라, 위치를 키에 넣으면 하나도 안 묶인다. 반올림은 SVG 파서가 만든 부동소수 오차를 흡수하기 위한 것 — 눈으로 같은 모양이면 같은 키가 나와야 한다
	- **⚠️ 비싸다. 매 프레임 부르면 안 된다.** 개체의 모든 점을 `String(format:)`으로 이어 붙이는 계산이라 개체 하나에 점 수십 개면 그만큼 걸린다. 반드시 `AppEnvironment`의 쌍둥이 인덱스(2.4절)를 거쳐 쓸 것 — 이 규칙을 어겨서 화면이 멈춘 적이 있다(엔진 디버깅 1-1번)

SVG 좌표와 위경도를 **다른 타입**으로 못 박아, Anchor 변환을 거치지 않은 좌표가 GeoJSON에 새는 것을 컴파일 타임에 막는다.

- `struct GeoPoint { var longitude: Double; var latitude: Double }` — GeoJSON 순서(경도, 위도)와 필드 순서를 일치시킴

#### `EditorLayer.swift`
명세 2항·4항의 레이어 네 종류를 하나의 타입으로 표현.
- `enum LayerKind { case baseTop, baseGhost, attributeFilter(StyleKey), propertyType(IMDFFeatureType) }`
- `var isClosable: Bool` — `baseTop`/`baseGhost`는 false
- `var isHidable: Bool` — `baseGhost`만 false
- `var allowsObjectActions: Bool` — `baseGhost`만 false
- `var opacity: Double` — `baseGhost`는 0.2
- **개체 목록을 복사해 들고 있지 않는다**(2026-08-26 확정, `07) 성능 최적화 제안.md` 제안 6). 초안에 있던 `visibleObjectIDs: Set<VectorObjectID>` 조항은 폐기했다 — 레이어 10장이면 개체 id 집합이 10벌 생기고 개체 하나가 태깅될 때마다 10벌을 모두 고쳐야 한다. 한 벌이라도 빠지면 레이어마다 보이는 것이 달라지는, 원인 찾기 어려운 버그가 된다. 표시 여부는 `AppEnvironment.renderStates()`가 레이어의 **규칙**(`kind`)으로 판정하고, 그 결과만 캐시한다. 속성 필터 레이어의 후보는 `objectIDsByAttributeKey` 색인이 즉시 준다(복사가 아니라 색인이다)

#### 레이어별 투명도 (2026-08-27 요청)
`EditorLayer.opacity` — 레이어 목록의 각 줄 아래에 슬라이더가 붙는다.

- **기본값과 사용자 값을 따로 둔다**(`baseOpacity` / `customOpacity`). 하위 기본 레이어의 50%는 명세 2-3이 정한 수치라, 사용자가 만진 뒤에도 **되돌릴 기준**이 남아 있어야 한다. `hasCustomOpacity`가 참일 때만 되돌리기 버튼이 뜬다
- **0%로는 내려가지 않는다**(하한 5%). 0%는 레이어가 사라진 것과 같은데 그건 '숨기기'가 할 일이다 — 숨긴 것은 눈 아이콘으로 되돌릴 수 있지만, 투명도 0은 화면에서 이유를 알 수 없다
- **활성 레이어의 값이 그리기 투명도에 곱해진다**(`computeRenderState`). 상위 기본·property type·속성 필터 레이어에서 그려지는 개체는 지금 열려 있는 레이어의 것이기 때문이다. **하위 기본 레이어(고스트)는 따로 그려지므로 자기 값을 쓴다** — 원위치 대조용이라 작업 레이어를 옅게 했다고 함께 옅어지면 대조가 안 된다
- **슬라이더를 레이어 줄 바로 아래 둔다.** 팝오버나 별도 창으로 빼면 값을 바꾸는 동안 도면이 가려져, 얼마나 옅어졌는지 보면서 맞출 수가 없다
- 숨긴 레이어에서는 슬라이더를 잠근다 — 만져도 아무 변화가 없으면 고장으로 읽힌다

- `var requiredGeometry: GeoJSONGeometryKind?` — `01)` 문서의 geometry 열 그대로(unit=Polygon, opening=LineString, fixture=MultiPolygon, amenity=Point, address/occupant=null 등)

- **대여는 opening → 타 type 한 방향뿐이다.** 반대 방향(벽이 소유하고 opening이 빌림)은 만들지 않는다 — 추출하는 것이 좌표뿐이라 소유 주체가 결과를 바꾸지 않고, 양방향을 허용하면 순환 참조만 생긴다(명세 10-2-6)
- `var hasDisplayPoint: Bool` — 명세 7-3-4)의 버튼 노출 조건. `01)` 문서 기준 amenity(부분)·building·fixture·level·unit(부분)·venue가 true, opening은 항상 null이므로 false

#### `PropertySchema.swift`
`Resources/FeatureSchemas.json`을 디코딩한 결과. **`01) geojson 파일별 properties 구조.md`의 표가 이 JSON의 원본**이다.

#### `PropertyValue.swift`

- `func validate(against field: PropertyField) -> ValidationResult`

#### `DisplayPoint.swift`

- `func geoJSON(using: Georeferencer) -> [String: Any]` — 명세 7-3-4-2)의 `{"type":"Point","coordinates":[lon,lat]}` 형태 그대로

#### `Segmentation.swift`

명세 9-3)의 Anchor 한 쌍. **점 하나가 아니라 두 점이 짝을 이룬다** — 이것이 Anchor 설계의 핵심이다.
- `let id: AnchorID`

#### `ProjectFile.swift`
`.ftiproj` 저장 포맷(Codable). SVG 원본은 파일 안에 복사 저장해, 원본이 옮겨져도 세션이 깨지지 않게 한다.

- 저장 대상: 원본 SVG 데이터, feature 그룹 전체, 레이어 구성, **Anchor 쌍**, **선분화 상태**, **발급된 UUID 대장**(발급분 + 폐기분), 휴지통.

- UUID 대장이 저장 대상인 이유는 스타일 문제가 아니라 스펙 요건이다. IMDF는 "Feature IDs MUST be retained... across distinct deliveries"를 요구하므로, 프로젝트를 닫았다 열고 다시 내보내도 같은 feature가 같은 UUID를 가져야 한다(0.1절 4번).

#### `OwnershipRegistry.swift`

#### `BorrowRegistry.swift`
명세 10항의 opening 빌려주기. `OwnershipRegistry`와 **일부러 분리한 별개 자료구조**다 — 소유는 배타적이고 대여는 그렇지 않으므로, 같은 딕셔너리에 섞으면 배타성 검사가 무너진다.

- `private var borrowedBy: [VectorObjectID: Set<FeatureGroupID>]` — **값이 `Set`인 것이 핵심.** 방 A와 방 B 사이의 문은 양쪽 폴리곤을 모두 닫아야 하므로 **하나의 opening을 여러 feature가 동시에 빌린다**(명세 10-2-5)
- `func borrow(_ ids: Set<VectorObjectID>, for feature: FeatureGroupID) throws` — 대상이 opening 소유가 아니면 `BorrowError.notAnOpening`, 빌리는 쪽 type이 `canBorrowOpenings == false`면 `BorrowError.typeCannotBorrow`

- `func borrowers(of objectID:) -> Set<FeatureGroupID>` — opening을 휴지통에 보낼 때 경고 대상을 찾는다(명세 10-4-4)
- `func borrowed(by feature: FeatureGroupID) -> Set<VectorObjectID>`
- **진행률에 영향을 주지 않는다.** 분자는 `OwnershipRegistry.claimedCount`만 쓰므로 빌려간 개체가 중복 계산되지 않는다(명세 10-3-3)

#### `UndoStack.swift`
cmd+z / cmd+shift+z(디버깅 8번, 2026-08-25). `EditorSnapshot`(되돌릴 상태 전부) + `UndoStack`(칸 목록).
- **명령별 역연산이 아니라 통째 스냅샷이다.** 작업 단위가 서로 얽혀 있기 때문 — feature 하나를 저장하면 `features`·`ownership`·`serials`·`selection`·`expandedFeature`가 함께 바뀌고, 그룹 해제는 거기에 `ids`(폐기 UUID 대장)까지 건드린다. 역연산을 명령마다 따로 쓰면 새 명령을 추가할 때 되돌리기를 빠뜨리고, 그 실패는 "되돌렸는데 소유권만 남아 있다" 같은 **조용한 상태 붕괴**로 나타난다

- `record(_:coalescingKey:before:)` — 같은 `coalescingKey`가 연달아 오면 새 칸을 쌓지 않는다. 속성 입력칸은 **글자 하나마다** `updateProperty`를 부르므로, 합치지 않으면 이름 한 번 입력에 실행취소가 열 칸씩 쌓여 스택이 쓸모없어진다. 직전 칸이 이미 입력 시작 전 상태를 들고 있으므로 되돌아갈 지점은 정확하다
- `discardLast()` — `AppEnvironment.perform`이 "실행했는데 상태가 그대로면" 부른다. 빈 칸이 쌓이면 cmd+z를 눌러도 화면이 안 바뀌는 것처럼 보인다
- 새 작업을 하면 `redoEntries`를 버린다. 갈라진 미래를 남겨두면 어느 쪽으로 가는지 알 수 없다
- 도면을 새로 열면 `clear()`. 다른 도면의 칸을 남겨두면 cmd+z 한 번에 지금 문서에 없는 개체 id로 상태가 덮인다
- **되돌리기 대상에서 뺀 것(`확인 필요`):** 개체 개별 선택 토글(클릭마다 칸이 쌓이면 60칸이 선택 이력으로 차서 정작 되돌릴 작업이 밀려난다), 보조 개체 창의 창 전용 선택(창을 닫으면 사라지는 임시 상태). '전체 선택 해제'는 파괴적이라 포함
- 모든 Store에 `Equatable`을 붙였다 — `perform`이 "바뀐 게 있나"를 판단하려면 스냅샷 비교가 필요하다

### 2.3-1 Model/ProjectFile.swift — 작업 저장 (명세 7-3-2·9-7, 2026-08-25 구현)

**이 파일이 없으면 IMDF 스펙을 지킬 수 없었다.** 스펙은 Feature id에 대해 "MUST be retained to identify the target feature during the lifetime of its existence **across distinct deliveries**"를 요구한다 — 두 번째 내보내기에서도 같은 UUID가 나와야 한다. 앱을 닫을 때 `IDAssigner`가 사라지면 다시 열었을 때 새 UUID가 발급되어 그 요건이 깨진다. 폐기 UUID 대장(`retired`)도 같은 이유로 함께 저장한다("MUST NOT be re-assigned").

- **SVG 원본을 통째로 담는다. 경로만 참조하지 않는다.** 도면 파일이 옮겨지거나 이름이 바뀌면 프로젝트가 통째로 열리지 않게 되는데, 이 앱의 작업 결과(수십~수백 개의 태깅)는 도면 파일 하나보다 훨씬 비싸다. SVG는 텍스트라 함께 담아도 파일이 크게 늘지 않는다
- 담는 것: `features` · `ownership` · `segmentation` · `auxiliary` · `anchors` · `serials` · `ids` · `openingGate` · `borrow`
- **담지 않는 것: 선택 상태 · 펼친 feature · 레이어 목록 · 사이드바 폭 · 실행취소 스택.** 전부 "지금 화면을 어떻게 보고 있는가"이지 작업 결과가 아니다. 저장하면 열 때마다 남의 화면 상태가 따라오고, 실행취소 스택은 다른 세션의 칸을 되살려 지금 문서에 없는 상태로 덮어쓸 위험이 있다
- 여는 쪽에서 **저장된 feature의 type만큼 property type 레이어를 되살린다.** 레이어 목록을 저장하지 않으므로, 안 되살리면 feature는 있는데 담을 레이어가 없어 우측 사이드바가 비어 보인다
- **`version` 필드를 두고 앞선 버전은 거부한다.** 모르는 필드를 버린 채 열고 저장하면 사용자의 작업이 소리 없이 사라진다
- **날짜 인코딩에 ISO8601을 쓰지 않는다.** 사람이 읽기는 좋지만 **초 미만을 잘라** 저장했다 여는 것만으로 `createdAt` 값이 달라진다. "저장하고 다시 열면 같은 상태"라는 보장이 읽기 편함보다 중요해서 기본 전략(실수 초)을 쓴다. 자체점검이 왕복 동일성을 검사하며, 실제로 이 문제를 여기서 잡았다
- 키를 정렬해 쓴다. 같은 상태를 두 번 저장하면 파일이 동일해져, 버전 관리 도구에 넣었을 때 의미 없는 변경이 쌓이지 않는다
- 새 SVG를 열면 `projectURL`을 비운다. 남겨두면 `저장`이 이전 작업 파일을 덮어쓴다
- 메뉴: `작업 열기…`(cmd+shift+O) · `작업 저장`(cmd+S) · `다른 이름으로 저장…`(cmd+shift+S)

### 2.3-2 저장 루프·종료·작업 공유 (신기능 1항, 2026-08-25 구현)

구현 위치: `Model/StableObjectID.swift` · `Model/Assignment.swift` · `App/ProjectPersistence.swift`.
셋을 한 절에 묶은 이유는 **하나의 이야기**이기 때문이다 — 30초마다 저장하고, 닫을 때 마저 저장하고, 그 저장 형식을 그대로 남에게 넘긴다.

#### 개체 id를 도면에서 결정적으로 뽑는다 — 이 절 전체의 전제
`StableObjectID.make(ordinal:element:styleKey:geometry:)`. 예전에는 파싱할 때마다 `UUID()`를 새로 발급했다.

- **그러면 작업 공유가 원리적으로 불가능하다.** 같은 SVG를 A와 B가 각자 열어도 개체 id가 서로 달라, B가 태깅한 결과를 A에 붙일 때 **어느 개체를 태깅한 것인지 가리킬 이름이 없다.**
- 신기능 1-2-6의 "**어떤 좌표들을 기준으로** 벡터가 할당되었는지 기억해야 한다"가 정확히 이 요구다. 그래서 좌표에서 뽑는다
- 좌표 + `ordinal` + 요소 종류 + 스타일 키를 이어 붙여 SHA-256 앞 16바이트를 UUID로 쓴다
	- **좌표를 넣는 이유:** 같은 모양이라도 자리가 다르면 다른 개체다
	- **`ordinal`을 함께 넣는 이유:** 완전히 같은 자리에 같은 도형이 두 번 그려진 도면(작도 실수)에서도 둘을 갈라야 한다. 파싱 순서는 같은 SVG라면 항상 같으므로 결정성이 깨지지 않는다
	- 좌표는 0.001까지만 쓴다 — 나중에 파서가 미세하게 바뀌어도 id가 통째로 갈리지 않도록 여유를 둔다
- `DrawingDocument.fingerprint` — 개체 id 전체의 해시. **같은 도면인지 확인하는 두 번째 자물쇠다.** `projectID`가 같아도 도면을 바꿔 열면 개체가 통째로 달라진다
- **버전 1 파일은 열지 않고 거절한다.** 읽을 수는 있지만 읽으면 안 된다 — 지금 코드로 그 SVG를 다시 읽으면 완전히 다른 id가 나오므로, 저장된 태깅이 가리키는 개체가 도면에 하나도 없는 상태로 열린다. 화면에는 정상처럼 보이는 **조용한 데이터 손실**이라 열어 주는 쪽이 더 나쁘다
- **확장자는 `.imdfrnt`다.** 한때 `.imdfproj`로 바꿨다가 사용자 지시로 되돌렸다(2026-08-25). **그 결과 버전 1과 버전 2가 같은 확장자를 쓴다** — 파일 이름으로는 구분되지 않고 `version` 필드가 유일한 판별 수단이다. 확장자를 보고 안심하면 안 된다
	- 되돌리기 전 잠깐 쓰인 `.imdfproj`도 열기 창에서 고를 수 있게 남겼고(`interimFileExtension`), **자동 저장본도 이어받는다**(`interimAutosaveURL`). 이 자리를 안 봐주면 확장자를 바꾼 그 순간 사용자의 마지막 작업이 사라진다 — 파일은 멀쩡히 있는데 앱이 다른 이름만 찾으니 "저장했다더니 없어졌다"가 된다. 실제로 되돌릴 때 `autosave.imdfproj`에 3MB가 쌓여 있었다

#### 자동 저장 (신기능 1-1-1)
`AppEnvironment.autosaveInterval = 30` · `startAutosaveLoop()` · `autosaveTick()`.

- 화면에 아무것도 띄우지 않는다(명세대로). 30초마다 배너가 뜨면 그것만으로 작업이 방해된다
- **바뀐 게 없으면 아예 쓰지 않는다**(`snapshot != lastSavedSnapshot`). 파일 시각만 계속 갱신되면 사용자가 파일 목록에서 "언제 뭘 했는지"를 읽을 수 없다
- **안전망 파일에는 항상 쓰고, 사용자가 정한 위치가 있으면 거기도 같이 쓴다.** 안전망만 쓰면 사용자 파일이 낡고, 사용자 파일만 쓰면 위치를 안 정한 사람에게 안전망이 없다. 위치는 `~/Library/Application Support/IM-DFrnt/autosave.imdfproj`
- 저장 조건은 `hasProjectContent`(태깅 결과가 있는가)가 아니라 **`hasSomethingToPersist`(도면이 열려 있는가)**다. 도면을 다시 찾아 여는 것 자체가 작업이다
- **손 저장(`saveProject`)도 같은 `persist(showingBanner:)`를 탄다.** 손 저장과 자동 저장이 서로 다른 코드로 파일을 만들면 둘의 결과가 갈릴 수 있다

#### 복원 — 명세에 없지만 없으면 저장이 무의미하다
`restoreAutosaveIfAvailable()`. **저장만 하고 복원하지 않으면 사용자 입장에서는 저장이 없는 것과 같다.** 1-1-3의 "종료해도 작업이 모두 저장돼요"가 성립하려면 다시 켰을 때 돌아와야 한다. (`04) 엔진 디버깅.md` 2-1번도 이것으로 닫힌다.)
- 열기와 복원이 **같은 `adopt(_:from:)`을 탄다.** 둘이 갈리면 한쪽만 되살리는 항목이 생기고, 그 차이는 "어제 작업이 일부만 돌아왔다"는 형태로 나중에야 드러난다
- 복원 뒤 `projectURL`을 되찾아 준다(`UserDefaults`). 안 그러면 복원 직후의 `저장`이 "다른 이름으로 저장" 창을 띄운다
- 복원 실패로 앱이 안 뜨면 안 된다. 빈 화면으로 시작하되 이유는 알린다

#### 종료 (신기능 1-1-2·1-1-3)
`confirmTermination()` + `AppDelegate`.
- **cmd+Q · 메뉴 종료 · 창 닫기가 모두 한 곳을 지난다.** 명세는 "창 닫기"만 말하지만, cmd+Q가 확인 없이 빠져나가면 "모두 저장돼요"라는 약속이 그 경로에서만 깨진다
- **창 닫기는 닫지 않고 종료 경로로 넘긴다**(`windowShouldClose` → `NSApp.terminate` → `false`). 먼저 닫아 버리면 '아니오'를 눌러도 돌아갈 화면이 없다
- **'저장 안 함' 버튼을 일부러 두지 않았다.** 명세가 저장을 약속하므로 건너뛰는 길이 있으면 약속이 거짓말이 된다. 되돌리려면 cmd+z, 다른 결과를 남기려면 '다른 이름으로 저장'이 있다
- 종료 알림은 **앱 안 배너**로 띄우고 실제 종료를 1.2초 미룬다(`.terminateLater`). 시스템 알림은 권한을 요구하는데, 종료 한 번 알리려고 권한을 묻는 것은 과하다
- 도면이 없으면 묻지 않는다. 빈 앱을 닫는 데 확인을 받으면 성가시기만 하다

#### `Assignment` — 1-2-6을 '자르지 않는 방식'으로 푼 것
요구는 "도면을 어떤 방향으로 잘랐는지, 다시 붙일 때 어떻게 붙일지 기억"이다. **실제로 자르지 않는 것으로 풀었다.**

- 조각을 잘라 보내면 B가 맥락을 잃는다 — 방 하나를 태깅하려면 옆방 벽선이 보여야 한다
- 잘라 보낸 조각을 다시 붙이려면 좌표를 맞추는 계산이 필요하고, 그 계산이 틀리면 조용히 어긋난다
- **도면 전체를 보내고 "여기부터 여기까지가 당신 몫"만 표시한다.** 좌표계가 처음부터 하나뿐이라 붙일 때 맞출 것이 없다. **가장 안전한 재조립은 재조립을 안 하는 것이다**
- 필드: `id`(같은 파일 두 번 합치기 방지) · `projectID`(원본 작업 신원) · `drawingFingerprint`(도면 신원) · `assignee` · `objectIDs`(**정본**) · `bounds`(표시용, 유도값) · `createdAt`
- `bounds`와 `objectIDs`가 어긋나면 **`objectIDs`를 따른다**

#### 배정본을 연 쪽의 제약 (신기능 1-2-4)
`isWithinAssignment(_:)`. 담당 밖 개체는 **보이지만 고를 수 없다.**
- 도면 전체가 보이는 것은 맥락 때문이고, 고를 수 있는 것과는 다른 문제다
- 표시는 기존 **'비활성' 색을 그대로 쓴다.** 상태를 새로 만들면 사용자가 배워야 할 것이 늘어난다 — 뜻이 "고를 수 없다"로 같으므로 색을 나눌 이유가 없다
- **클릭(`handleCanvasClick`)과 드래그 선택(`marqueeAdmission`) 양쪽에 같은 규칙을 건다.** 한쪽만 막으면 경로마다 규칙이 갈린다(디버깅 9번에서 같은 형태의 실수를 이미 겪었다)
- 배정본은 **다시 배정할 수 없다**(`canShareAssignment`). 몫을 또 쪼개면 합칠 때 어느 조각이 어디 속하는지가 흐려진다

#### 합치기 (신기능 1-2-5)
`mergeAssignments()` → `merge(file:named:into:report:)`.
- **파일 읽기와 병합 본체를 분리했다. 떼어낸 이유는 검증 때문이다** — 합치기는 잘못되면 남의 작업이 소리 없이 사라지거나 내 작업을 덮는 종류인데, 디스크를 거치면 `--selftest`가 확인할 방법이 없다
- **좌표를 맞추는 계산이 여기 없다는 점이 핵심이다.** 개체 id가 도면 좌표에서 결정적으로 나오므로 양쪽의 같은 개체는 처음부터 같은 이름을 갖는다
- 거절하는 것: 다른 `projectID` · 지문 불일치 · 배정본 아님 · 담당 밖을 태깅해 온 feature · 이쪽에서 이미 주인이 정해진 개체
	- **덮어쓰지 않는다.** 어느 쪽이 맞는지는 사람이 판단할 일이지 합치기가 정할 일이 아니다
- **`MergeReport`로 무엇이 왜 막혔는지 반드시 보여준다.** 조용히 건너뛰면 내보내기 단계에서야 드러난다
- **발급된 UUID를 그대로 물려받는다**(`IDAssigner.adopt`). 새로 뽑으면 IMDF 스펙의 "distinct deliveries 사이 id 유지" 요건이 담당자 몫에서만 조용히 깨진다
- 일련번호를 `reserve`한다. 안 하면 다음 저장에서 번호가 겹친다
- **선분화는 결과를 옮기지 않고 같은 개체를 이쪽에서 다시 계산한다.** 원본 도형에서 결정적으로 나오므로 결과가 같고, 남의 파일에서 온 좌표 배열을 그대로 믿는 것보다 안전하다
- 전체를 `perform("배정본 합치기")`로 감싼다 — cmd+z 한 번으로 통째로 되돌릴 수 있다

#### UI 위치 (신기능 1-2-1)
좌측 사이드바 헤더(제목 + 접기 버튼) **바로 아래 첫 항목**. 배정본을 열고 있으면 같은 자리에 **공유 버튼 대신 담당 구역 안내**를 보여준다 — 받은 사람에게 필요한 정보는 "내가 다시 나눠줄 수 있는가"가 아니라 "내 몫이 어디까지인가"다. 같은 자리에 다른 것을 놓는 편이 항목을 늘리는 것보다 낫다. 메뉴에도 같은 두 항목을 두되, 사이드바가 정식 입구이고 메뉴는 단축 경로다.

### 2.4-1 Store/ — Opening 선행 태깅과 문 빌려주기 (명세 10항, 2026-08-25 구현)

**「디버깅 완료」 5번에 '설계·구현'으로 적혀 있었으나 실제 코드에는 판정 함수 `IMDFFeatureType.canBorrowOpenings` 하나뿐이었다.** 그 함수조차 `--selftest` 외에는 호출자가 없어, 명세 10항 전체가 동작하지 않는 상태였다. 2026-08-25에 Store 계층과 게이트·대여 로직을 구현했다.

#### `OpeningGateStore`
opening을 다른 property type보다 먼저 태깅하도록 강제하는 게이트(명세 10-1).
- **완료 '선언'이지 '판정'이 아니다.** 도면에 문이 몇 개인지 프로그램이 알 수 없으므로 자동 판정이 원리적으로 불가능하다. 사용자가 `opening 태깅 완료`를 눌러야 다른 메뉴가 열린다(명세 10-1-3)
- `AppEnvironment.selectPropertyType(_:)`이 게이트를 본다. opening 자신은 언제나 열린다
- **`reopen()` — 되돌릴 수 있다**(명세 10-1-4). 빠뜨린 문을 발견하면 돌아가 추가하며, **이미 저장한 다른 feature는 건드리지 않는다.** 게이트는 메뉴만 잠그지 데이터를 손대지 않는다
- 문 없는 도면도 허용하되 경고를 **한 번만** 띄운다(명세 10-1-5). 매번 띄우면 통과 의례가 된다

#### `BorrowRegistry`
문 빌려주기 장부(명세 10-2).
- **`OwnershipRegistry`와 같은 자료구조에 섞지 않는다.** 소유는 배타적이고(개체 하나에 주인 하나) 대여는 **비배타적**이다 — 방 A와 방 B 사이의 문은 양쪽 폴리곤을 모두 닫아야 하므로 두 feature가 같은 문을 동시에 빌린다(명세 10-2-5). 한 딕셔너리에 넣으면 배타성 검사가 무너져 opening이 흡수되고 파일에서 사라진다
- `feature → 빌린 개체들` 한 방향만 저장한다(명세 10-2-6). 역방향 조회가 필요한 곳은 `borrowers(of:)`가 훑어서 만든다 — 양방향 장부는 두 벌을 동기화해야 하고, 어긋나면 폴리곤이 조용히 열린다
- `giveBack`에서 **빈 항목을 지운다.** 남겨두면 '빌린 게 있는 feature' 판정이 참이 되어 인스펙터에 빈 섹션이 뜬다

#### 대여가 걸리는 지점
- **선택**(`toggleSelect`) — 소유권 배타 규칙의 **유일한 예외**다. `canBorrow`가 참이면 명세 4-1) 경고창을 띄우지 않고 그냥 선택된다(명세 10-2-1·2). 경고를 띄우면 정상 작업이 매번 막힌다
- **저장**(`createFeature`) — 빌려온 opening을 **소유 주장에서 뺀다.** 소유권이 옮겨 가면 opening 레이어에서 사라지고 진행률 분자에 두 번 세어진다(명세 10-3-2·3). 구성원(`memberIDs`)에도 넣지 않는다 — IMDF에 "이 unit이 저 opening을 빌렸다"를 적을 필드가 없기 때문이다(명세 10-5-2)
- **빌린 것만으로는 저장할 수 없다.** 아무것도 소유하지 않는 빈 feature가 생긴다

### 2.4-2 문 임시로 닫기 (신기능 3항, 2026-08-25 구현)

구현: `Model/TemporaryDoor.swift` · `Geometry/SnapPointExtractor.swift` · `App/DoorClosure.swift` · `UI/DoorClosure/` 2파일.

#### 왜 대여(2.15)로는 안 되는가 — 이 절의 출발점
방은 문 자리에서 벽이 끊겨 있고, 그 틈은 지금까지 **opening 개체를 빌려서** 메웠다(`BorrowRegistry`). 그건 **도면에 문선이 그려져 있을 때** 성립한다.
**문이 열린 상태로 그려진 도면에는 닫는 데 쓸 선분이 아예 없다** — 문짝과 회전 궤적(호)만 있다. 빌릴 대상이 없으므로 대여로는 링이 닫히지 않는다.
그래서 사용자가 끊긴 자리의 **두 점을 직접 찍어 없는 선분을 만든다.**

#### `FeatureGroup.closureSegment` — 개체가 아닌 좌표를 싣는 자리
- 찍은 선분은 **도면에 없으므로 `memberIDs`로 표현할 수 없다.** 결과가 개체가 아니라 좌표다
- 이 값이 있으면 opening의 LineString 좌표는 **구성원이 아니라 이 선분**에서 나온다(`VertexExtractor` 첫 분기)
	- **구성원으로 LineString을 만들면 호를 따라 휘어진 엉뚱한 선이 나온다.** 문짝과 호는 문의 *모양*이지 문이 지나는 *자리*가 아니다
- 구성원(문짝·호)은 "이 opening이 도면의 무엇을 소비했는가"를 남기는 쪽으로만 쓰인다 — 소유권과 진행률이 거기 걸린다

#### `SnapPointExtractor` — 아무 데나 못 찍게 하는 것이 요점
신기능 3-2: "모든 개체는 '끝점'과 '교차점'을 선택 가능".
- **눈대중으로 근처를 찍으면 몇 단위씩 어긋나고, 그 틈으로 폴리곤이 다시 열린다.** 화면에서는 닫힌 것처럼 보이는데 내보내기에서 실패하는 종류의 오류다
- 끝점: 열린 경로의 양 끝. 닫힌 경로는 '끝'이 없다
- 교차점: **서로 다른 개체**의 선분이 실제로 가로지르는 자리(`OverlapDetector.crossing` 재사용). 같은 개체의 자기 교차는 보지 않는다 — 작도 흔적일 때가 많고 문 자리를 닫는 데 쓸 점이 아니다
- **같은 자리에 둘 다 성립하면 끝점이 이긴다.** 벽선이 T자로 만나는 자리가 그렇다. 사용자가 찍으려는 것은 "벽이 끝난 자리"이지 "두 선이 만난 자리"가 아니다
- `mergeTolerance = 0.05`로 같은 자리를 합친다. 도면은 벽선 두 개가 꼭짓점에서 만나도 좌표가 소수점 아래에서 어긋나 있는 일이 흔하다
- 결과를 정렬해 반환한다. 화면 표시가 아니라 **재현성** 때문이다 — 딕셔너리 순서를 그대로 내보내면 실행할 때마다 목록이 달라져 자체점검이 흔들린다
- `nearest(to:among:within:)`은 허용 반경 밖이면 **아무것도 주지 않는다.** 억지로 가장 가까운 점을 주면 의도하지 않은 자리에 선분이 걸린다
- **끝점·꼭짓점·교차점 세 종류를 낸다.** 같은 자리에 여러 종류가 성립하면 **뜻이 좁은 쪽이 이긴다: 끝점 > 교차점 > 꼭짓점.** "벽이 끝난 자리"가 가장 좁고, "두 개체가 가로지른 자리"가 그다음이며, "한 개체가 꺾인 자리"는 도면 어디에나 있다. 벽선이 사각형 모서리에서 끝나면 셋 다 성립하는데 사용자가 겨냥한 것은 끝점이다
	- **꼭짓점을 넣기 전에는 닫힌 경로에 후보가 하나도 없었다.** 방 폴리곤은 닫힌 경로라 '끝'이 없어서, 정작 문 자리 양옆의 방 모서리를 찍을 수 없었다
	- 종류가 어느 쪽으로 정해지든 **주인(`owners`)은 언제나 합친다.** 벽선 두 개가 한 점에서 끝나거나 모서리를 공유하는 것은 도면에서 흔하다
	- 화면에서는 모양으로 가른다: 끝점 ○ · 교차점 □ · **꼭짓점 ◇**. 꼭짓점은 수가 압도적으로 많아 더 작고 옅게 그린다 — 같은 크기로 그리면 도면이 마커로 덮여 정작 끝점이 안 보인다
	- **화면에 들어오는 후보만 그린다.** 꼭짓점까지 넣으면 실도면에서 마커가 수만 개가 되는데, 매 프레임 다 그리면 창이 멈춘다. 안 보이는 것을 그리지 않는 것은 결과를 바꾸지 않으면서 가장 크게 줄이는 방법이다
- **후보 목록은 창에 들어갈 때만 만든다**(`enterDoorClosureScreen`). 처음에는 도면 적재 시점(`document`의 `didSet`)에 만들었는데, **그 상태로 실제 자동 저장본(3.3MB, 개체 수천 개)을 복원하니 앱이 켜지다 멈췄다.** 계산이 개체 수의 제곱에 붙는 것을 만드는 시점으로 풀어야 한다는 것을 두 번째로 배운 자리다(엔진 디버깅 1-1과 같은 실수)
- **교차점 판정은 경계 상자로 먼저 거른다.** 개체 상자 → 선분 상자 → 실제 교차 순으로 좁힌다. 도면에서 실제로 겹치는 개체 쌍은 전체의 아주 일부라, 상자만 봐도 대부분이 끝난다. 거르지 않으면 창에 들어가는 순간 멈추므로, **시점을 미루는 것만으로는 부족했다**
- `--selftest`는 자동 저장본을 복원하지도, 저장 루프를 돌리지도 않는다. SwiftUI의 `onAppear`가 `applicationDidFinishLaunching`보다 먼저 도는 경우가 있어 막지 않으면 점검이 진짜 사용자 파일을 읽는다 — **점검 결과가 그날 작업 내용에 따라 달라지면 점검이 아니다**

#### 문짝 / 호 판정 — 사용자가 아니라 도형이 정한다
`toggleDoorObject`는 `isCurved`로 자리를 정한다. 곡선이면 호, 직선이면 문짝.
- **호는 회전 궤적이라 반드시 곡선이므로 이 판정은 도면이 보장한다**
- 버튼으로 "지금 문짝을 고르는 중"을 먼저 정하게 하면 클릭 한 번마다 모드 전환이 하나씩 더 붙는다
- 문짝과 호를 **다른 색**으로 그린다(선택색 / pending색). 둘 다 선택 색이면 무엇이 무엇으로 잡혔는지 확인할 방법이 없고, 곡선 판정이 틀렸을 때 알아챌 수 없다
- 점은 두 개까지만 받고 세 번째는 가장 오래된 것을 밀어낸다. 매번 지우고 다시 찍게 하면 손이 두 배로 든다

#### 저장과 반영을 나눈 이유 (3-5·3-6)
`DoorClosureStore`에 모아 뒀다가 '모두 Openings 레이어에 반영하기'로 한 번에 넘긴다.
- **문 하나마다 즉시 반영하면** 도면 전체를 훑는 동안 우측 인스펙터가 계속 흔들리고 **실행취소 칸이 문 개수만큼 쌓인다.** 반영은 칸 하나다
- 반영 시점에 문짝·호가 이미 다른 feature 소유면 **덮지 않고 건너뛰며, 목록에 남긴다.** 지워 버리면 사용자가 무엇을 잃었는지 알 수 없다(3-8: 소유권 배타 규칙을 이 경로에서도 그대로 따른다)
- 길이 0인 문은 저장을 막는다. GeoJSON으로 나가면 그대로 깨진 opening이 된다

#### 진행률 (3-7)
`claimedCount`가 `ownership.claimedObjectIDs`와 `doorClosures.consumedObjectIDs`의 **합집합**을 센다.
- 반영 전에도 세는 이유: 사용자 입장에서는 이미 처리한 개체인데 막대가 안 움직이면 한 줄 알 수 없다
- 합집합으로 세는 이유: 반영 뒤에는 `ownership`에도 잡히므로 **이중 계산이 100% 초과로 샌다**

#### 반드시 저장·되돌림 대상에 넣는다
- `ProjectFile.doorClosures` — 도면 전체를 훑으며 수십 개를 찍는 작업이라 앱을 닫았다고 사라지면 그 작업량이 통째로 날아간다. 기본값을 둬서 이 필드가 없는 옛 파일도 그대로 열린다
- `EditorSnapshot.doorClosures` — **빠뜨리면 `perform`이 "바뀐 게 없다"고 판단해 실행취소 칸을 도로 버린다.** cmd+z를 눌러도 아무 일이 안 일어나는 종류의 버그다
- 새 도면을 열면 비운다. 임시 문은 개체 id를 들고 있어 다른 도면에서는 없는 개체를 가리킨다

#### `DoorClosureAppearance.excludedOpacity = 0.2` (3-1)
**`EditorLayer.baseOpacity`를 빌려 쓰지 않았다.** 그 값은 하위 기본 레이어용이고 2026-08-25 사노 요청으로 20% → 50%가 됐다. 우연히 같았던 수치를 한 곳에 묶으면 한쪽 요구가 바뀔 때 다른 쪽이 조용히 끌려간다.

#### 창 안 드래그 규칙
그냥 드래그는 **화면 이동**이다(사각형 선택 아님). 고를 것이 점과 개체 두 종류뿐이고 둘 다 하나씩 지정하는 것이라 여러 개를 훑을 일이 없고, 확대한 채로 도면을 훑는 시간이 대부분인 작업이다.

#### 진입 조건
좌측 사이드바 '문 임시로 닫기'. **Openings 레이어일 때만 눌린다** — 다른 type에서 열어 주면 사용자가 만든 opening이 엉뚱한 레이어에 쌓인다. 버튼을 숨기지 않고 비활성으로 두고 도움말로 조건을 밝힌다(숨기면 "왜 없지"로 헤맨다).

### 2.4-4 좁힐 때의 레이아웃 규칙 (뷰 디버깅 16번, 2026-08-25)

**사이드바·창 크기를 조절할 때 컴포넌트와 글자가 어긋나던 문제.** 원인은 두 가지였고 둘 다 "폭을 숫자로 못 박은 것"에서 왔다.

#### 표는 `Grid`로 짠다 — 열 폭을 숫자로 정하지 않는다
- 우측 사이드바 좌표 표(110pt), Anchor 화면 쌍 표(170/110/190/90 = 560pt)가 그랬다. 사이드바는 260~620pt로 변하고 Anchor 표는 창 폭을 따라간다
- **Anchor 표는 어긋난 이유가 하나 더 있었다: 머리글과 값이 서로 다른 컨테이너에 있었다.** 머리글은 `HStack`, 값은 `ScrollView` 안의 다른 `HStack`이라, 폭을 똑같이 못 박아도 행에만 붙은 가로 여백과 끝의 삭제 버튼 때문에 세로줄이 밀렸다. **폭을 맞추는 것으로는 절대 안 맞는 구조였다**
- `Grid`는 **모든 행이 같은 열 폭을 공유**하므로 이런 어긋남이 구조적으로 생기지 않는다. Anchor 표는 머리글도 같은 `Grid`에 넣었다 — 스크롤과 함께 움직이는 대신 절대 어긋나지 않는다(쌍이 보통 3~8개라 스크롤될 일이 드물다)

#### 무엇이 먼저 줄어야 하는지를 명시한다
SwiftUI는 그냥 두면 한 줄의 모든 글자를 **고르게** 줄인다. 그래서 긴 설명이 아니라 **버튼 글자와 개수가 먼저 잘렸다**("레이어 생…").
- 긴 설명: `.lineLimit(1)` + `.truncationMode(.tail)` + `.layoutPriority(-1)` → **먼저 양보**
- 개수·버튼: `.fixedSize()` → **절대 안 줄어든다**
- 근거: 사용자가 눌러야 하는 것과 읽어야 하는 숫자가 잘리는 것이, 설명이 잘리는 것보다 나쁘다
- feature 일련번호만 `.truncationMode(.middle)`이다 — "unit-…-012"처럼 종류와 번호가 함께 보여야 어느 feature인지 알아본다

#### 여러 줄 안내문에는 `fixedSize(horizontal: false, vertical: true)`
없으면 좁을 때 **줄바꿈 대신 뒤가 잘려** 문장이 끊긴 채로 보인다. 사이드바 안 안내문 6곳이 그 상태였다.
**반대로 도면 위에 뜬 캡슐(범례·안내)은 한 줄로 자른다** — 줄이 늘면 도면을 덮는다. 같은 종류의 글자라도 놓인 자리에 따라 규칙이 반대다.

#### 검증 한계
**이 항목은 `--selftest`가 확인할 수 없다.** 렌더링 결과라 수치 규칙으로 떼어낼 부분이 없다. `06) 확인 필요.md` C 항목과 같은 성격이며, 창을 **가장 좁게 줄여서** 봐야 한다 — 넓을 때는 원래 멀쩡했다.

### 2.4-3 사이드바 '모두 접기' (2026-08-25 요청)

구현: `UI/SidebarSection.swift` + `AppEnvironment.collapsedSections`.

- **접힌 상태를 뷰가 아니라 `AppEnvironment`에 둔 이유가 '모두 접기' 그 자체다.** 각 섹션이 자기 `@State`를 들고 있으면 바깥에서 한 번에 바꿀 방법이 없다. 한 곳에 모으면 버튼은 키 목록을 넣고 빼기만 하면 된다
- `SidebarSectionID`에 `owner`를 둬서 **'모두 접기'가 자기 사이드바만 건드린다.** 한 버튼이 다른 창의 항목까지 접으면, 그 창에 갔을 때 접힌 이유를 알 수 없다
- **버튼은 전부 접히면 '모두 펼치기'로 바뀐다.** 접기만 있으면 되돌릴 방법이 항목을 하나씩 누르는 것뿐이다. 버튼을 두 개 두지 않는 이유는 둘 중 하나가 항상 아무 일도 안 하는 버튼이 되기 때문이다
- **우측 사이드바는 펼쳐 놓은 feature 카드까지 함께 접는다.** 거기서 자리를 가장 많이 차지하는 것이 카드다

##### 최상위 트리 폐지, 카드별 개별 토글 (2026-08-26 요청)

이전에는 카드 전부가 `SidebarSection(id: .rightFeatures, title: "FEATURES")` **하나의 트리 안에** 들어 있었고, 그 상위 토글을 누르면 목록이 통째로 접혔다. 사용자 지시로 그 상위 토글을 없애고, **'모두 접기' 버튼이 카드마다 달린 개별 토글을 한꺼번에 움직이도록** 바꿨다.

- **`SidebarSectionID.rightFeatures`를 제거했다.** `FEATURES`는 개수만 알려주는 표시 전용 머리글(`RightSidebar.featureListHeader`)이 됐다. 접고 펴는 것은 카드 각자의 몫이다. 우측에 남은 섹션은 `rightTrash` 하나뿐이다
- **`expandedFeature: FeatureGroupID?` → `expandedFeatures: Set<FeatureGroupID>`.** 한 칸이면 카드가 늘 하나만 펼쳐지고, 그 구조 때문에 상위 트리가 필요했다. 여러 개를 동시에 펼 수 있어야 카드별 토글이 뜻을 갖는다
- **초점(`focusedFeature`)을 따로 둔다.** 상단바의 display point 찍기처럼 **대상이 하나여야 하는** 동작이 이 값을 쓴다. 여러 카드가 펼쳐져 있을 때 무엇을 겨냥하는지 모호해지면 안 된다. 초점이던 카드를 접으면 **남아 있는 카드로 옮긴다** — 비워 두면 다른 카드가 펼쳐져 있는데도 대상별 동작이 사라진다
- 기존 호출부를 위해 `expandedFeature`는 `focusedFeature`를 읽고, 대입하면 그 하나만 펼친 상태가 되는 창구로 남겼다
- **빌려온 표시(`isBorrowedHere`)와 링 간격(`openRingGaps`)은 펼친 카드 전부를 본다.** 하나만 보면 옆 카드가 빌린 문이 소유한 것처럼 보이고, 열린 링 표시가 카드마다 나타났다 사라진다. 링 간격은 일련번호로 정렬해 모은다 — `Set`은 순서를 보장하지 않아, 정렬하지 않으면 같은 상태에서 표시 순서가 달라진다
- `EditorSnapshot`도 집합과 초점 두 칸으로 바꿨다(실행취소가 펼침 상태를 그대로 되돌린다)
- 검증: `--selftest` 6항목 신규(동시 펼침 · 하나만 접기 · 초점 이동 · 모두 접기 · 모두 펼치기 · **상위 트리가 없는지**)
- **접힌 항목에도 개수·진행률을 배지로 남긴다.** 접는 목적은 자리를 줄이는 것이지 상태를 감추는 것이 아니다. 접어 두면 아무것도 모르게 되면 결국 다시 펴게 된다
- 제목 줄 전체가 눌린다. 화살표만 눌리면 표적이 10pt짜리가 된다
- Anchor 화면은 사이드바가 아니라 하단 패널이지만 같은 규칙을 적용했다. **접으면 패널 높이 자체가 줄어든다**(260 → 150) — 접었는데 높이가 그대로면 빈 칸만 남아 접는 의미가 없다
- **`ProjectFile`에도 `EditorSnapshot`에도 넣지 않는다.** 사이드바 폭과 같은 이유다 — "지금 화면을 어떻게 보고 있는가"이지 작업 결과가 아니다. 넣으면 cmd+z 한 번에 항목이 접혔다 펴지고, 남의 파일을 열 때 남의 화면 상태가 따라온다
- **그룹 해제·휴지통** — `giveBackAll`. 빌린 쪽이 사라지면 대여도 끝난다. 안 지우면 없는 feature가 opening을 붙잡고 있어 휴지통 경고가 유령 일련번호를 띄운다
- **`EditorSnapshot`에 게이트와 대여를 넣었다.** 대여가 안 돌아오면 실행취소 뒤 폴리곤이 열린 채 남는다
- 도면을 새로 열면 둘 다 초기화한다. 남겨두면 새 도면에서 다른 type 메뉴가 이미 열려 있어 선행 태깅이 통째로 건너뛰어진다

#### UI
- `LeftSidebar.openingGateBar` — property type 목록 **바로 위**에 둔다. 잠긴 이유를 목록 옆에서 즉시 읽어야 "왜 안 눌리지"로 헤매지 않는다(명세 10-1-2). 잠긴 동안에는 주황 배경으로 눈에 띄게 한다
- `RightSidebar` 인스펙터의 `빌려온 opening (N)` 섹션(명세 10-3-4). **구성원 목록과 분리한다** — 섞으면 "이 unit이 문을 소유한다"로 읽혀 소유·대여 구분이 무너진다. 개체 UUID 대신 소유 feature의 일련번호로 적는다

#### 빌려온 개체의 화면 표시 (명세 10-2-2, 2026-08-25)
"함께 선택 시 경고창을 띄우지 않는다. 대신 해당 개체를 **점선 테두리 + 다른 색**으로 표시해 '빌려온 것'임을 시각적으로 구분한다." 경고를 없앤 자리에 이 표시가 들어가야 하는데, 표시 쪽이 빠져 있어 **빌린 문이 내 개체와 똑같이 보였다.**
- `ObjectRenderState.isBorrowed` + `AppEnvironment.isBorrowedHere(_:)`
- **판정 대상이 둘이다:** ① 지금 펼친 feature가 이미 빌린 것 ② 지금 골라 놓은 것 가운데 빌릴 수 있는 것. 앞은 빌린 상태, 뒤는 저장하면 빌리게 될 상태 — **사용자에게는 둘 다 "내 것이 아닌 문"**이라 같이 표시한다
- **빌림은 특정 feature와의 관계지 개체의 속성이 아니다.** 관계없는 화면(아무것도 펼치지 않고 고르지도 않은 상태)에서는 표시하지 않는다
- 색은 소유·비활성·선택 어느 것과도 다른 값을 쓴다. 같은 색이면 "내가 저장한 것"과 "남에게 빌린 것"이 구분되지 않는다
- **원본이 점선이든 실선이든 빌린 동안에는 같은 점선으로 덮어쓴다.** 상태 표시가 도면 원본 스타일에 따라 달라지면 알아볼 수 없다

#### 빌려온 opening이 좌표에 들어가는 경로 (명세 10-3-1·10-5-2, 2026-08-25)
**대여 장부만 만들고 좌표 추출에 연결하지 않으면 빌려주기 기능 전체가 무의미하다.** `VertexExtractor.vertices`가 `memberIDs`만 보고 있어서, 문을 빌려도 **열린 폴리곤 좌표가 그대로 파일로 나갔다.**
- `vertices(for:document:segmentation:kind:borrowed:)` — 빌려온 개체 id를 함께 받아 구성원과 합쳐 좌표를 뽑는다. 구성원 목록 자체는 건드리지 않는다(명세 10-3-1: "좌표 계산에만 참여")
- **`GeoJSONGeometryKind.usesBorrowedOpenings` — 폴리곤 계열에만 넣는다.** LineString에 남의 문을 이으면 선이 엉뚱한 데로 뻗고, Point는 중심이 문 쪽으로 끌려간다. 링을 닫는 것이 목적이므로 닫을 링이 있는 geometry만 해당한다
- `GeoJSONExporter`·`ExportValidator`가 `BorrowRegistry`를 받는다
- **인스펙터 좌표 표(`vertexRows`)도 같은 인자로 뽑는다.** 화면 표와 파일이 갈라지면 사용자가 표를 보고 확인한 것이 파일에서는 다른 값이 된다 — 명세 7-3-5의 좌표 표는 내보낼 것을 미리 보여주는 화면이다

#### `Geometry/RingClosureValidator.swift` — 링 닫힘 검증 (명세 10-4, 2026-08-25)
**눈으로 붙어 보여도 미세하게 벌어져 있으면 폴리곤은 닫히지 않는다.** CAD 도면은 선 끝이 정확히 맞물리는 일이 드물다. Esri ArcGIS Indoors의 대응 개념이 `Door Close Buffer` — "used to account for poor CAD topology — for example, line gaps between doors and walls."

- **판정은 끝점 짝짓기다.** 닫힌 링에서는 모든 끝점이 다른 선분의 끝점과 만나 짝수 번 쓰인다. 홀수로 남은 끝점이 곧 벽이 끊긴 자리 — 대개 문이 뚫린 곳이다. **면적·방향 대신 이 방식을 쓰는 이유는 어디가 벌어졌는지를 좌표로 짚어야 하기 때문**이다(명세 10-4-3이 "어느 지점인지 캔버스에 표시"를 요구한다). 닫혔는지만 알면 되는 판정이면 훨씬 단순한 방법이 있다
- 같은 선분의 반대쪽 끝은 짝으로 세지 않는다 — 그건 변 자신이다
- 오차보다 짧은 선분은 링의 변으로 세지 않는다. 점이나 다름없어 판정이 흔들린다
- 한 자리에서 여러 번 잡힌 틈은 하나로 줄인다. 벌어진 곳 하나가 양쪽 끝점에서 잡히면 사용자에게는 두 곳으로 보인다. 큰 틈부터 정렬한다 — 손으로 고칠 때 그쪽이 먼저다

##### `mismatchWarning`과의 역할 분담 (2026-08-25)
`GeometryClassifier.mismatchWarning`의 polygon 분기가 **"닫힌 subpath가 하나도 없으면 경고"** 였는데, 이는 틀린 판정이었다.
- **벽 선분 네 개로 그린 방은 닫힌 subpath가 하나도 없어도 링이 닫힌다.** 문을 빌려 닫는 경우(명세 10항)는 더더욱 그렇다. 그런데 이 경고가 `ExportValidator`를 거쳐 **내보내기 차단**으로 이어졌으므로, 정상 도면의 정상 작업을 막고 있었다
- polygon 계열의 `anyClosed` 검사를 **없앴다.** 두 함수의 역할을 이렇게 가른다:
  - `mismatchWarning` — geometry **종류**가 어긋나는 경우만(LineString인데 닫힌 도형, geometry가 null이어야 하는데 개체가 있음). 이건 차단 사유가 맞다
  - `RingClosureValidator` — 링이 실제로 닫히는지. **경고일 뿐 차단하지 않는다.** 도면을 고쳐 다시 저장하는 것이 정상 흐름이라 막으면 작업이 통째로 묶이고, 명세 7-4의 차단 조건에도 링 열림은 없다
- `openRingFeatures(type:)` — 내보내기 직후 배너로 알린다. **type을 받아 그 레이어 것만 본다**: 내보내기는 한 type씩 하므로 다른 레이어의 열린 링까지 알리면 방금 만든 파일과 무관한 경고가 섞인다. 어느 feature인지 일련번호로 짚어 줘야 인스펙터에서 찾아갈 수 있다

##### 앱 계층 연결
- `AppEnvironment.ringClosure(of:)` — **빌려온 opening까지 넣고 판정한다.** 문을 빌리는 목적 자체가 그 선분으로 벽의 빈자리를 메우는 것이라, 빼고 재면 늘 열려 있다. 허용 오차는 겹침 판정과 같은 `overlapTolerance`(도면 크기 비례)
- `requiresClosedRing` — geometry가 Polygon/MultiPolygon인 type만 판정한다. amenity는 점 하나라 닫을 링이 없다
- **저장을 막지는 않는다.** 경고만 띄운다 — 도면을 고쳐 다시 저장하는 것이 정상 흐름이고, 저장 자체를 막으면 작업하던 선택이 통째로 날아간다. 명세 7-4의 내보내기 차단 조건에도 링 열림은 없으므로 추가하지 않았다
- **경고 문구에서 단위를 mm로 단정하지 않는다.** SVG 도면 좌표에는 단위가 없고 실제 거리는 지오레퍼런싱 후에야 안다. Anchor가 갖춰졌으면 mm로, 아니면 도면 단위로 적는다 — **없는 정확도를 지어내면 사용자가 도면을 잘못 고친다.** 환산은 벌어진 거리만큼 옮긴 점을 함께 변환해 재며, 변환에 회전·비등방 축척이 섞여 있어 상수를 곱하는 식으로는 환산되지 않는다
- `openRingGaps`는 **펼쳐 놓은 feature 기준의 계산 속성**이다. 저장 직후에는 그 feature가 펼쳐지므로 배너 경고와 자동으로 같은 곳을 가리키고, 나중에 다시 펼쳐도 같은 자리가 표시된다. 별도 상태로 들고 있으면 둘이 어긋나 "경고는 뜨는데 화면에는 표시가 없는" 상태가 생긴다
- 캔버스 표시는 **점선 원 + 가운데 짧은 선**. 겹침 윤곽(`#FF00D9` 마름모)과 색·모양을 일부러 다르게 했다 — 겹침은 "여기 뭔가 있다", 이쪽은 "여기가 비어 있다"로 뜻이 정반대라 같은 기호를 쓰면 도면을 반대로 고치게 된다
- 인스펙터에도 상시 표시한다. 저장 순간의 배너는 곧 사라지므로 나중에 상태를 다시 확인할 곳이 필요하다
- **휴지통 경고(명세 10-4-4)** — opening을 버리기 **전에** 빌려 쓰는 feature 일련번호를 알린다. 지우고 나서 알리면 이미 폴리곤이 열린 뒤다

### 2.5 Geometry/

#### `CurveFlattener.swift`
명세 8-4)의 '선분화'. 곡률에 비례해 쪼갠다(균등 분할이 아니라 적응 분할 — 완만한 구간에 점을 낭비하지 않기 위해).
- `func flatten(_ geometry: PathGeometry, tolerance: Double) -> [LineSegment]`
- `private func subdivideCubic(_:tolerance:) -> [LocalPoint]` — de Casteljau 적응 분할
- `var defaultTolerance: Double` — 설정에서 조절 가능하게 노출(구버전 문서 2.2절의 "근사 정밀도 파라미터화" 결론 계승)
- **반환 타입이 `PathGeometry`가 아니라 `[LineSegment]`인 것이 중요하다.** 명세 8-4-3)이 "하나로 이어진 폴리라인이 아니라 개별 선분"을 요구하기 때문이다. 이어진 path로 반환하면 그 요구를 표현할 수 없다

#### `SegmentationValidator.swift`
명세 8-4-3)의 두 가지 제약을 기하학적으로 검사한다. `CurveFlattener` 출력을 `SegmentationStore`가 받아들이기 전에 반드시 통과해야 한다.
- `func validate(_ segments: [LineSegment], epsilon: Double) -> [SegmentationDefect]`
- `enum SegmentationDefect { case gap(index: Int, distance: Double); case crossing(Int, Int, at: LocalPoint) }`
- `private func checkContiguity(...)` — 인접 선분의 끝점이 `epsilon` 안에서 **반드시 만나는지**. 어긋나면 `gap`
- `private func checkNonCrossing(...)` — 인접하지 않은 선분끼리 내부를 가로지르는지. 가로지르면 `crossing`. 인접 선분이 공유 끝점에서 만나는 것은 교차가 아니다
- 적응 분할은 원리상 gap을 만들지 않지만, 부동소수 누적 오차와 닫힌 경로의 시작/끝 접합에서 실제로 벌어질 수 있어 검사가 필요하다. 결함이 나오면 tolerance를 낮춰 재시도하고, 그래도 남으면 사용자에게 알린다

#### `RingCloser.swift`
명세 10-4)의 검증. 빌려온 opening이 실제로 링을 닫았는지 판정한다. **눈으로 붙어 보여도 미세하게 벌어져 있으면 폴리곤이 안 된다.**

- `func close(owned: [LineSegment], borrowed: [LineSegment], tolerance: Double) -> ClosureResult`
- `enum ClosureResult { case closed([LocalPoint]); case open(gaps: [(LocalPoint, LocalPoint, Double)]) }` — 실패 시 어느 지점이 몇 mm 벌어졌는지 함께 반환해 캔버스에 표시한다(명세 10-4-3)
- `var defaultTolerance: Double` — Esri의 `Door Close Buffer`에 대응하는 값. 원문은 이 값의 목적을 "used to account for **poor CAD topology** — for example, line gaps between doors and walls"로 설명한다. Esri 참조 페이지에 기본값이 명시되어 있지 않아 초기값 결정은 미정(0.2절)
- 반환된 점 배열은 `VertexExtractor.orderedRing`이 그대로 쓸 수 있는 **경로 순서**여야 한다. 빌려온 opening 선분이 링의 한 변으로 들어가기 때문에, 벽 선분과 문 선분을 섞어 순회하는 로직이 필요하다

#### `VertexExtractor.swift`
명세 7-3-5)를 그대로 옮긴 파일. feature 그룹 하나의 **좌표 변환 대상 꼭짓점 목록**을 낸다.
- `func extractVertices(for feature: FeatureGroup, in document:) -> [LocalPoint]` — `memberIDs` **∪ `borrowedIDs`**를 대상으로 한다. 빌려온 opening의 양 끝점이 링의 꼭짓점이 되고 문 선분이 링의 한 변이 되어 폴리곤이 닫힌다(명세 10-3-1)
- `private func polygonVertices(...)` — 교차점 + 미교차 끝점(7-3-5-1). 닫힌 단일 경로는 경로 순서가 곧 링이라 그대로 쓰지만, **스스로를 가로지르는 닫힌 경로는 이 지름길에서 제외**하고 아래 `polygonRing`으로 넘긴다 — 경로 순서를 믿으면 지나쳐 찍힌 꼭짓점이 그대로 좌표가 된다
  - **(2026-08-25 2차) 꼬리 끝점을 버리는 규칙에 대해 사노가 "그대로 꼬리 끝점 버리기"로 확정했다.** 도면에 따라 그 꼬리가 실제 좌표일 수 있다는 우려가 있었으나 현재 규칙을 유지하기로 결정, 추가 구현 없음.
- `func polygonRing(from segments:) -> [LocalPoint]` — **「디버깅 5번」의 본체(2026-08-25)**. 두 선분이 꼭짓점에서 만나지 않고 **서로를 가로질러** 지나가면, 링의 꼭짓점은 교차점이고 교차점을 지나쳐 뻗은 끝점은 작도 흔적이다. 그 끝점을 그대로 내보내면 방 폴리곤이 별 모양으로 삐져나온다. 판정은 세 단계다
	1. **교차 판정은 `OverlapDetector.crossing`을 그대로 호출한다.** 같은 계산을 두 벌 두지 않기 위해서다 — '만나는 점(양쪽 다 끝점에서 만나는 꼭짓점 접합)은 교차가 아니다'라는 기준이 겹침 윤곽 표시와 좌표 추출에서 갈라지면, 화면에 교차로 표시된 지점이 좌표에는 안 들어가는 식으로 어긋난다
	2. `private func isInterior(_:of:)` — 교차점이 그 선분의 **내부**인지. 양쪽 선분 모두 내부를 지날 때만 X자로 가로지른 것이다. **T자 접합(한쪽 끝점이 상대 선분 위에 얹힌 경우)은 자르지 않는다** — 지나친 꼬리가 애초에 없고, 그 자유 끝점은 명세 7-3-5-1)이 명시적으로 요구하는 좌표다
	3. 가로질린 선분의 끝점은 버린다. 단 **다른 선분의 끝점과 맞닿아 있으면 남긴다** — 작도 흔적이 아니라 실제 접합이기 때문. 끝점 동일성은 좌표를 소수점 4자리로 양자화한 키로 센다
- 결과적으로 "지나치게 그린 사각형(`#`자로 모서리마다 삐져나온 벽 4개)"은 교차점 4개, 즉 안쪽 사각형만 남는다. 끝점끼리 정확히 맞닿게 그린 정상 사각형은 아무것도 바뀌지 않는다
- 교차점 계산이 `SegmentationValidator.properIntersection`에서 `OverlapDetector.crossing`으로 바뀌었다. 전자는 T자 접합을 아예 버리는데, 그 지점은 어차피 끝점 수집에서 같은 좌표로 다시 들어오므로 결과는 같고 기준만 하나로 모인다
- `private func lineStringVertices(...)` — 선분 양 끝점(7-3-5-2)
- `private func pointVertex(...)` — 점 좌표(7-3-5-3)
- `private func multiPolygonVertices(...)` — polygon 규칙의 집합(7-3-5-4)
- `func orderedRing(from points:) -> [LocalPoint]` — GeoJSON Polygon은 **순서 있는 링**을 요구하므로, 추출된 점 집합을 실제 경로 순서로 재배열하는 단계가 반드시 필요하다(명세에는 없지만 출력 형식상 필수)

#### `OverlapDetector.swift`
선택한 개체가 다른 벡터와 겹치는 곳을 찾는다. **명세 2-3)의 '위치 이동'을 대체하는 기능**(2026-08-25 확정) — 개체를 옆으로 밀어 아래를 확인하는 대신, 겹치는 지점의 윤곽을 제자리에 `#FF00D9`로 표시한다.
- `static func detect(selected:among:segmentation:tolerance:) -> Result` — 선택 집합 전체를 한 번에 본다
- `struct Result { crossings: [LocalPoint]; sharedSegments: [LineSegment]; partnerIDs: Set<VectorObjectID> }` — 겹침을 두 형태로 나눠 담는다. 표시 모양이 다르기 때문이다(교차점은 마름모 마커, 공유 구간은 굵은 선)
- `static func crossing(_:_:) -> LocalPoint?` — 두 선분이 실제로 **가로지르는** 지점. **양쪽 다 끝점에서 만나는 꼭짓점 접합은 nil이다** — 방 폴리곤 모서리끼리 맞닿은 정상 도면이 전부 겹침으로 잡히면 표시가 의미를 잃는다. 이 '만나는 점 vs 교차점' 구분은 「디버깅 미완」 5번과 같은 기준이므로 **`VertexExtractor.polygonRing`이 이 함수를 그대로 호출한다**(2026-08-25). 이 함수를 고치면 겹침 표시와 좌표 추출이 함께 바뀐다는 뜻이니, 판정 기준을 손댈 때는 양쪽을 같이 봐야 한다
- `static func sharedRun(_:_:tolerance:) -> LineSegment?` — 같은 직선 위에서 겹쳐 지나가는 구간. 벽이 이중으로 그려진 경우가 여기 잡힌다
- 중복 제거: 인접 선분마다 같은 교차점이 반복 검출되므로 tolerance 크기 격자로 양자화해 한 번만 담는다
- 성능: 개체별 선분 목록과 bounding box를 미리 캐시하고, box가 안 겹치면 선분 루프를 아예 돌지 않는다. 둘 다 선택된 쌍은 `uuidString` 순서로 한쪽만 본다

#### `HitTester.swift`
캔버스 클릭 좌표 → 개체 판정. stroke만 있는 개체는 두께 기반 허용오차를 준다.
- `func hitTest(_ point: LocalPoint, candidates:segmentation:tolerance:) -> VectorObjectID?` — 2026-08-25에 `offsets` 파라미터가 사라졌다(개체 이동 폐지)
- `func objects(in rect:mode:candidates:segmentation:) -> [VectorObjectID]` — **드래그 사각형 선택**(디버깅 9번, 2026-08-25). 명세 5항의 금지 조항이 이날 뒤집혔다
	- `enum MarqueeMode { case enclose, crossing }` — 도면 CAD의 관례. 좌→우는 통째로 들어온 것만, 우→좌는 닿기만 해도. **두 방향을 다 두는 이유:** 도면에서는 벽선 하나가 화면 밖까지 뻗어 있는 일이 흔해 `enclose`만으로는 영영 못 고르고, `crossing`만 두면 방 하나를 고르려다 지나가는 벽까지 딸려온다
	- `crossing`은 bounding box가 겹치는 것으로 만족하지 않고 **실제 선분까지** 본다. box만 보면 대각선으로 지나가는 선이 엉뚱하게 잡힌다
	- 채워진 개체는 예외로 사각형 중심의 내부 판정을 추가로 본다 — 면 안에서 작게 드래그하면 선분은 안 닿지만 사용자 눈에는 그 개체를 긁은 것이다
	- 속이 빈 개체의 안쪽만 훑은 것은 **아무것도 안 스친 것**이 맞다
- `func segment(_:intersects rect:) -> Bool` — 선분·사각형 교차. 끝점이 안에 있거나 네 변 중 하나와 교차하면 참. 관통하는 선(끝점이 둘 다 밖)을 놓치지 않기 위한 것이다

##### 화면별 드래그 규칙
| 화면 | 그냥 드래그 | 사각형 선택 | 근거 |
|---|---|---|---|
| 메인 캔버스 | 화면 팬 | **fn+shift+z 드래그** | 명세 5항의 "실수 선택 방지" 장치를 그대로 잇는다 |
| 보조 개체 제외 창 | **사각형 선택** | 그냥 드래그 | 이 창은 클릭도 수식키 없이 먹는다. 드래그만 예외로 두면 "클릭은 되는데 드래그는 안 되는" 상태가 된다. 화면 이동은 ⌥드래그·두 손가락 스크롤 |
| Anchor 지정 화면 | 마커 드래그 / 화면 팬 | **해당 없음** | 이 화면에는 고를 벡터 개체가 없다. 도면은 배경이고 조작 대상은 Anchor 마커뿐인데, 마커에는 다중 선택 개념도 일괄 명령도 없다 |

- `AppEnvironment.handleMarqueeSelection(rect:mode:)` / `.handleAuxiliaryMarquee(rect:mode:)`
	- **클릭 경로와 판정 규칙은 똑같이 두되 막혔을 때의 반응만 다르다.** 클릭은 하나를 겨냥한 행동이라 못 고르면 경고창을 띄워야 하지만, 드래그는 수십 개를 훑는 행동이라 개체마다 경고를 띄우면 작업이 멈춘다 → **조용히 건너뛰고 개수만 요약**(`3개 선택 · 보조 개체 2개 제외`)
	- `marqueeAdmission(_:in:) -> .allow / .curvedOnly / .auxiliary / .owned` — 거절 사유를 `handleCanvasClick`과 1:1로 맞춘 지점. 둘이 어긋나면 "클릭으로는 되는데 드래그로는 안 되는" 개체가 생긴다
	- **토글이 아니라 더하기다.** 수십 개를 한꺼번에 뒤집으면 이미 고른 것이 딸려 풀려 결과를 예측할 수 없다
	- 보조 개체 창 쪽은 소유권을 보지 않는다 — 거기서 고르는 것은 'feature 구성원'이 아니라 '태깅 대상에서 뺄 것'이라 이미 저장된 개체도 골라야 정상이다

#### 위치 이동 재도입 (명세 2-3, 2026-08-25 2차, 사노 요청)
`03) 뷰 디버깅.md` 4번의 확인 필요 항목에 사노가 "그냥 이동 다시 가능하게 하기"로 답하면서, `06) 확인 필요`에 있던 A2가 결정으로 바뀌었다. 겹침 윤곽 표시(대체 기능으로 만들었던 것)를 없애지 않고 **공존**시켰다.
- **`AppEnvironment.transientOffsets: [VectorObjectID: CGSize]`** — 개체별 화면 이동량. 명세 원문 "이동된 위치는 영구 저장되지 않음"을 그대로 지킨다 — `EditorSnapshot`(실행취소)에도, `ProjectFile`(작업 저장)에도 넣지 않는다. 도면을 새로 열거나(`load`) 프로젝트를 열면(`openProject`) 비운다(다른 도면의 이동량이 새 도면의 다른 개체 id에 씌워지는 것을 막는다).
- **좌표 추출·내보내기는 이 값을 보지 않는다.** `VertexExtractor`·`GeoJSONExporter`는 항상 `DrawingDocument`의 원본 좌표를 직접 읽는다 — 이동은 화면 전용이라는 명세 원문을 코드 경로로 강제한다.
- **`AppEnvironment.displayGeometry(for:)`** — 렌더링·클릭 판정 전용. `geometry(for:)`(세그멘테이션 반영)에 오프셋만 얹는다. `CanvasView`의 메인 오브젝트 렌더링만 이 함수를 쓰고, `AuxiliaryDrawingPane`은 기존 `geometry(for:)`를 그대로 쓴다(그 화면은 이동 제스처가 없다 — 다만 이미 옮긴 개체는 그 화면에서도 옮긴 자리로 보인다. 같은 문서·같은 개체이므로 일관된 편이 낫다고 판단했다).
- **드래그 판정(`CanvasView.dragGesture`)**: 드래그 시작점이 fn+shift+z 없이 눌렸고(`isSelectModeActive == false`) 그 점이 **지금 선택된 개체 위**(`AppEnvironment.movableHit`)면 이동, 아니면 팬이다. fn+shift+z를 누른 드래그(사각형 선택)가 최우선이라 판정 순서가 겹치지 않는다. `movableHit`은 `mode == .idle`일 때만 동작한다 — Anchor 찍기·display point 찍기·곡선 창 등 다른 모드에서는 드래그가 각자의 뜻을 가지므로 이동이 끼어들지 않는다.
- **델타는 시작점 기준 절대값이다.** `beginMove()`가 드래그 시작 시점의 오프셋을 스냅샷으로 찍어 두고, `applyMove(_:from:)`이 매 프레임 `시작 오프셋 + 전체 이동량`을 대입한다. 프레임마다 델타를 누적하면 반올림 오차가 쌓인다.
- **`HitTester.hitTest`·`HitTester.objects(in:mode:)`에 `offsets` 파라미터를 되살렸다**(기본값 `[:]`이라 기존 호출부는 그대로 컴파일된다). 옮긴 개체는 옮긴 자리에서 클릭·드래그 선택이 맞아야 하기 때문이다.
- **`원위치` 버튼 2곳** — 상단바(선택분만, `env.selectionHasOffset`일 때만 노출)와 `도구` 메뉴 `모든 개체 원위치`(`env.hasAnyOffset`일 때만 활성). 선택분과 전체를 나눠, 다른 곳에서 옮겨 둔 개체를 실수로 되돌리지 않게 했다.
- 검증: `--selftest` 314항목 전부 PASS(이동 8항목 신규 — 오프셋 반영·화면 지오메트리 이동·델타 절대값·**좌표 추출은 원본 좌표 사용**·선택분 원위치·전체 원위치). 앱 번들 재빌드 완료. GUI(실제 드래그)는 실행하지 않았다.
- **알려진 한계:** 겹침 윤곽 표시(`overlapHighlight`)는 여전히 원본(미이동) 좌표로 계산한다. 개체를 옮긴 상태에서 겹침 표시를 켜면, 마커는 원래 자리에 그려지고 개체 그림은 옮긴 자리에 그려져 시각적으로 어긋난다. 두 기능을 통합할지는 다음 확인 필요 항목으로 남긴다.

  4. `선분화` — `VectorObject.isCurved`가 하나라도 true일 때만 활성. 이미 선분화된 개체만 선택돼 있으면 `선분화 해제`로 라벨이 바뀐다(명세 8-4-4)
- `private var enabledButtons: Set<ToolbarButton>` — 활성 조건 판정을 한 곳에 모음

##### 그룹 해제와 opening 반납 (명세 8-2·10-2-3, 2026-08-25)
상단바에 **'그룹 해제'가 없었다.** 우측 사이드바에만 있어서 명세 8-2의 "그룹화 / 그룹 해제" 짝이 성립하지 않았고, 그것이 없으니 명세 10-2-3("빌려온 opening은 상단바의 그룹 해제 대상이 아니라 반납만 가능")도 걸 자리가 없었다.
- **대상은 지금 펼쳐 놓은 feature(`expandedFeature`)다.** 이미 저장된 개체는 선택할 수 없으므로 '선택으로 대상을 지정'하는 경로 자체가 성립하지 않는다. 라벨에 일련번호를 넣어 무엇이 해제되는지 못박는다
- **`opening N개 반납`은 그룹 해제와 다른 기능이다.** 해제는 feature를 없애지만, 반납은 "이 방은 그대로 두되 이 문은 안 쓰겠다"는 뜻이라 **폴리곤만 다시 열린다.** `BorrowRegistry.giveBack`을 쓰는 유일한 자리다(그룹 해제·휴지통은 `giveBackAll`)
- 반납 배너에 "이 폴리곤은 다시 열립니다"를 함께 적는다. 결과가 곧 링 열림이라, 모르고 누르면 나중에 저장 경고를 보고서야 원인을 찾게 된다

### 2.13 UI/CanvasChrome/ — 캔버스 조작 (프로토타입에서 추가)

명세에 없지만 실사용에 필요해 프로토타입 단계에서 추가한 것들이다. 도면 좌표를 바꾸지 않는 **표시 전용** 기능이라는 점이 공통이다.

#### `ZoomEventMonitor.swift`
커서를 초점으로 하는 확대·축소. SwiftUI `MagnificationGesture`는 배율만 주고 **확대 중심 좌표를 주지 않아** 커서 기준 확대를 만들 수 없다. 그래서 `NSEvent` 로컬 모니터로 `.scrollWheel`·`.magnify`를 받아 `locationInWindow`를 함께 쓴다.
- `var onZoom: ((CGPoint, CGFloat) -> Void)?` / `var onPan: ((CGFloat, CGFloat) -> Void)?`
- `var canvasFrame: CGRect` — 이 영역 밖 이벤트는 그대로 흘려보내 사이드바 스크롤을 막지 않는다
- 마우스 휠은 확대, 트랙패드 두 손가락은 이동, ⌘+스크롤은 어느 쪽이든 확대 — `hasPreciseScrollingDeltas`로 장치를 구분한다
- **로컬 모니터라 입력 모니터링 권한이 필요 없다.** 전역 모니터(`addGlobalMonitorForEvents`)를 쓰면 권한 요청이 뜨므로 쓰지 않는다
- 보정식: `offset' = anchor − (anchor − offset) × next / current`

#### `CanvasZoom.swift` — 확대 한계와 선 두께 (2026-08-25, "확대가 더 크게" 요청)
**세 작업 화면이 함께 쓰는 확대 규칙.** 한 곳에 모은 이유는 상한이 제각각이었기 때문이다 —
메인 8배 / 보조 개체 창 20배 / Anchor 화면 20배. **정작 태깅을 하는 주 화면이 가장 덜 확대됐고**,
화면마다 숫자를 따로 적어 두면 이런 어긋남을 알아챌 방법이 없다.

- `minScale = 0.1` / `maxScale = 200` — 하한은 세 화면 중 가장 관대하던 값에 맞췄다
- **상한만 올리면 확대가 소용없어진다. 이 절의 핵심이다.**
	- `Canvas`가 `scaleBy(s)`로 좌표를 늘리므로 **선 두께도 s배로 함께 늘어난다.** 8배까지는 티가 안 나지만 200배에서는 벽선 하나가 화면을 덮어, **더 크게 볼 수는 있는데 아무것도 안 보이는** 상태가 된다
	- `strokeWidth(_:at:emphasis:)` — `strokeGrowthCap`(4배) 시점의 화면 두께에서 성장을 멈춘다
	- **4배 이하에서는 계산 결과가 종전과 완전히 같다.** 지금까지 보던 화면이 안 바뀐다. 자체점검이 0.5·1·2·4배 각각에서 이것을 확인한다
	- 200배에서 화면상 4pt로 고정된다(보정 전 200pt)
	- **얇아지는 쪽(축소)은 건드리지 않았다.** 이번 요청은 확대이고, 축소 규칙을 같이 바꾸면 지금 잘 보이는 화면까지 흔들린다
- `screenLength(_:at:)` — 배율과 무관하게 **화면상 크기가 일정해야 하는** 것의 도면 좌표 길이(선택 강조 테두리·모서리 반경·빌림 표시 점선 간격). 보정하지 않으면 200배에서 선택 테두리가 개체에서 화면 밖까지 멀어진다
	- **원본 점선(`style.dashPattern`)은 보정하지 않는다.** 그건 도면이 가진 성질이라 확대와 함께 커지는 게 맞다. 빌림 표시 점선은 앱이 얹은 표시라 보정한다 — 둘을 같은 규칙으로 묶으면 한쪽이 반드시 틀린다
- `label(_:)` — 10배부터 `×` 표기. `20000%`는 자릿수가 넘쳐 칸을 벗어나고, 그 구간에서는 사람도 백분율보다 배수로 생각한다
- 마커·교차점·display point·Anchor 십자·겹침 윤곽은 **이전부터 `/scale` 보정이 되어 있었다.** 이번에 새로 보정한 것은 개체 선 두께와 선택 강조 테두리다

#### 캔버스 회전 (`AppEnvironment.canvasRotation`)
도면을 90° 단위로 좌우 회전. 도면이 세로로 긴데 화면은 가로로 넓은 경우가 흔하다.
- `func rotateCanvas(_ quarterTurns: Int)` — 0~3 순환
- **표시 전용이며 도면 좌표는 바뀌지 않는다.** Anchor 쌍과 추출 좌표가 회전에 영향받으면 안 되기 때문이다. 회전은 `GraphicsContext`에서 문서 중심을 축으로 적용하고, `toLocal`이 역회전으로 되돌린다
- 개체 드래그도 `toLocalDelta`로 방향을 역회전시켜야 한다 — 안 하면 회전 상태에서 개체가 엉뚱한 방향으로 움직인다
- `fit()`은 90°·270°에서 가로세로를 바꿔 계산한다

#### `CanvasBackground` (`AppEnvironment.swift`)
배경 밝게/어둡게 전환. 단순 색 교체가 아니다 — **검은 선 도면을 어두운 배경에서 열면 아무것도 보이지 않는다.**
- `func resolve(_:) -> Color` / `func resolveFill(_:) -> Color` — 선·채움 색의 상대 휘도를 배경 휘도와 비교해 차이가 0.28 미만이면 반전. SVG 원본 색은 보존하고 표시할 때만 반전하므로 '같은 속성 모아보기' 비교 기준에는 영향이 없다
- `defaultStroke` · `disabledStroke` · `selection` · `ghostStroke` · `marker(_:)` — **캔버스 위 요소는 `Color.secondary`·`.primary`·`.accentColor`를 쓰면 안 된다.** 그 색들은 캔버스 배경이 아니라 시스템 외관을 따라가므로, 시스템이 라이트인데 캔버스를 어둡게 두면 배경에 묻힌다
- **도면 위에 뜬 UI(줌 컨트롤·선택 상단바·모드 칩·범례·빈 화면 안내)도 캔버스 배경을 따른다**(`toolbarFill`·`toolbarForeground`·`toolbarStroke`, 디버깅 10번 2차). 종전에는 이것들을 "앱 크롬"으로 보고 머터리얼+시스템 외관에 맡겼는데, 머터리얼이 반투명이라 실질 바탕이 캔버스가 되면서 글자와 카드가 서로 다른 기준을 따라 묻혔다

#### `SidebarResizeHandle.swift` — `ResizableSidebar` (디버깅 1·13번, 2026-08-25)
사이드바 너비를 드래그로 조절. `NavigationSplitView` 대신 `HStack` 3분할이라 직접 만들었다.
**핸들만 있던 `SidebarResizeHandle`을 사이드바+핸들 컨테이너 `ResizableSidebar`로 바꿨다.**

- **드래그 중에는 폭을 로컬 `@State`(`dragWidth`)에만 쓰고, 손을 뗄 때 한 번만 `@Binding`에 확정한다.** 이 절의 핵심이다 — 폭을 `AppEnvironment`의 `@Published`에 매 프레임 쓰면 그 객체를 구독하는 뷰가 **전부**(캔버스·양쪽 사이드바) 매 프레임 `body`를 다시 계산한다. 캔버스는 도면 전체를 그리는 무거운 `Canvas`라 프레임이 밀리고, 그것이 "드래그하면 원위치에서 깜빡이다가 손을 떼야 옮겨지는" 증상이었다
- **왜 컨테이너여야 했나:** 핸들만으로는 사이드바의 `.frame(width:)`에 로컬 값을 먹일 수 없어 부모(=환경)를 거칠 수밖에 없다. 폭을 쓰는 쪽과 만드는 쪽이 같은 뷰 안에 있어야 로컬 상태로 닫힌다
- `enum SidebarResizeMath.width(base:translation:edge:range:)` — 방향 판정과 상·하한 고정을 뷰에서 떼어낸 순수 함수. **떼어낸 이유는 검증 때문이다:** 드래그 조작 자체는 `--selftest`가 재현할 수 없으므로 최소한 계산 규칙만은 헤드리스로 잡히게 한다(1번이 완료 보고 후 재발한 전례)
- 오른쪽 사이드바는 핸들이 왼편에 있어 드래그 방향이 반대다
- 제스처는 `minimumDistance: 0`, **좌표계는 전역(`.global`)**. 드래그로 이 뷰의 폭이 바뀌므로 로컬 좌표계를 쓰면 뷰가 움직인 만큼 `translation`이 어긋나 값이 발진한다
- 히트 영역 8px(보이는 선은 `Divider` 1px). 5px일 때는 겨냥이 자주 빗나갔다
- `.animation(nil, value:)` — 사이드바 접기의 `withAnimation(.easeOut)`이 드래그 폭까지 보간하면 커서보다 뒤처진다
- `NSCursor`는 상태를 하나 두고 **실제로 바뀔 때만** `push`/`pop` 한다. 횟수가 어긋나면 커서 스택이 쌓여 다른 화면에서도 화살표가 남는다. 드래그 중에는 커서가 핸들 밖으로 나가도 화살표를 유지한다
- **적용 범위:** 메인 3분할(좌·우) + 보조 개체 제외 창(`auxiliarySidebarWidth`, 320 고정이던 것). Anchor 화면은 `HSplitView`(AppKit 기본 분할)라 원래부터 매끄러워 대상이 아니다
- **폭은 `EditorSnapshot`에 넣지 않는다.** cmd+z가 창 크기를 되돌리면 정작 되돌리려던 작업 이력이 묻힌다
- 접기는 `AppEnvironment.showLeftSidebar` / `showRightSidebar`. 각 사이드바 헤더에 접기 버튼, 접힌 뒤에는 캔버스 모서리에 펼치기 버튼이 뜬다

##### 하위 기본 레이어는 활성이 될 수 없다 (명세 2-3, 2026-08-25)
`LayerStore.activeLayerID`를 `private(set)`으로 닫고 **`activate(_:)`로만 바꾼다.**
- **고스트 레이어가 활성이 되면 그 위에서 개체를 선택·저장할 수 있게 된다.** 원위치 확인용이라 어떤 액션도 허용되지 않는 레이어인데, 레이어 목록에서 행을 누르면 그대로 활성이 됐다. `EditorLayer.allowsObjectActions`는 정의만 있고 **아무도 읽지 않던 값**이었다
- 막을 곳을 **한 군데(`activate`)로 모은다.** 클릭 핸들러마다 조건을 걸면 새 진입 경로가 생길 때 빠뜨린다
- 클릭 시 아무 반응이 없으면 씹힌 것으로 오해하므로 이유를 배너로 알린다
- 고스트의 20% 불투명도는 `EditorLayer.baseOpacity` 한 곳에만 둔다. 캔버스가 `0.2`를 따로 적고 있어 수치가 두 곳에 흩어져 있었다 — 한쪽만 고치면 조용히 어긋난다

### 2.14 UI/LayerPanel/

#### `LayerListView.swift`
레이어 목록. 닫기/숨기기 버튼의 활성 여부는 `EditorLayer.isClosable` / `isHidable`이 결정한다(명세 2항). 구현 위치는 `UI/LeftSidebar.swift`의 `layerSection`.

##### 레이어가 화면을 실제로 바꾸게 연결 (2026-08-25)
**`renderState(for:)`가 활성 레이어를 전혀 참조하지 않아, 레이어를 만들어도 목록에 이름만 생기고 화면은 그대로였다.** 자료구조(`LayerKind.attributeFilter`, `EditorLayer.extraObjectIDs`, `LayerStore.addObjects`)는 처음부터 있었지만 호출자가 없었다. 세 가지를 이었다.

- **활성 레이어가 표시 여부의 1차 기준이다.** `attributeFilter`가 열려 있으면 `style.attributeKey`가 일치하는 개체 + `extraObjectIDs`에 든 개체만 보인다
- **`isHidden`이 렌더링에 반영된다.** 이전에는 눈 아이콘이 상태만 토글하고 화면이 안 바뀌었다 — 사용자에게는 고장으로 읽힌다. 하위 기본 레이어만 `isHidable == false`라 숨겨지지 않는다(명세 2-3, 원위치 확인용)
- **`AppEnvironment.addSelectionToActiveFilterLayer()`** — 명세 2항 "거기에 내가 선택한 다른 벡터들도 추가 가능". **필터 조건 자체는 건드리지 않고 개체 id만 따로 얹는다.** 속성이 달라 필터에 안 걸리는 개체를 같은 레이어에서 함께 다루려는 것이 이 기능의 목적이라, 조건을 넓히면 의도치 않은 개체까지 딸려 온다
- 레이어 **생성과 개체 추가 모두 `perform`을 거쳐 실행취소 대상**이다. 둘 다 화면에 보이는 개체를 바꾸므로, cmd+z로 직전 화면으로 못 돌아가면 손으로 레이어를 닫아야 한다
- `선택한 개체를 이 레이어에 추가` 버튼은 필터 레이어가 열려 있을 때만 뜬다 — 다른 레이어에서는 누를 대상이 없다

### 2.4-5 성능 구조 — 캐시와 무효화 (2026-08-26, `07) 성능 최적화 제안.md` 제안 1~6 반영)

레이어 캔버스를 드래그하기만 해도 멈추던 문제의 구조적 해결. **매 프레임 전부 다시 계산하던 것을 재료가 바뀔 때만 계산하도록** 바꿨다. 개별 근거와 전후 코드는 `07)` 문서에 있고, 여기에는 유지보수할 때 반드시 지켜야 할 규칙만 적는다.

**무효화는 `AppEnvironment`의 `@Published` 속성 `didSet` 한 곳에서만 한다.** 캐시를 지우는 코드를 여기저기 흩으면 새 기능이 들어올 때마다 한 군데씩 빠지고, 그때 증상은 "화면이 갱신되지 않는다"로 나타나 원인을 찾기 어렵다.

| 캐시 | 무엇을 담나 | 무효화 조건 |
| --- | --- | --- |
| `renderStateCache` (`renderStates()`) | 개체 id → 표시 상태 | `selection`·`ownership`·`features`·`layers`·`auxiliary`·`borrow`·`expandedFeature`·`mode`·`segmentation`·`assignment`·`document` |
| `RenderCacheStore` (`renderCache`) | 개체별 `Path`·선분·경계 상자 | **선분화가 바뀐 개체만** + 문서 교체 |
| `overlapHighlight` | 겹침 검사 결과 | `selection`·`segmentation`·`showOverlapHighlight`·`features`·`auxiliary`·`document` |
| `openRingGaps` | 링이 열린 지점 | `expandedFeature`·`features`·`borrow`·`doorClosures` |
| `objectIDsByAttributeKey` · `spatialIndex` | 속성 색인 · 64분할 격자 | 문서 교체 |

- **`renderState(for:)`의 이름과 동작은 유지한다.** 사전을 먼저 보고 없으면 그 자리에서 계산한다 — 기존 호출부와 `--selftest` 20여 곳을 고치지 않기 위해서다
- **원본 좌표는 도면이 열려 있는 동안 바뀌지 않는다**(이동은 화면 전용, 명세 2-3). 이것이 `RenderCacheStore`가 성립하는 근거다. 이 전제가 깨지는 기능(예: 좌표를 실제로 편집하는 기능)을 넣는다면 캐시 무효화를 함께 설계해야 한다
- **이동은 좌표를 옮긴 사본을 만들지 않는다.** 그리기는 `GraphicsContext`를 복사해 `translateBy`하고, 히트테스트·사각형 선택은 반대로 **클릭 좌표·사각형을 옮겨** 원본과 견준다
- **격자(`SpatialIndex`)는 원본 좌표 기준이라 옮긴 개체와 어긋난다.** 후보를 받을 때 `moved:`로 옮긴 개체를 항상 더한다 — 빠뜨리면 옮긴 개체가 클릭되지 않는다
- **`MoveSession`은 `@Published`가 아니다.** `@Published`로 두면 이동 한 프레임마다 `AppEnvironment`도 알림을 보내 사이드바까지 다시 그려진다 — 떼어낸 의미가 사라진다. 드래그가 끝났을 때만 `onSettled`로 한 번 알린다
- **`didSet`이 걸린 상태는 반복해서 고치지 않는다. 모아서 한 번에 대입한다.** 드래그 복수 선택이 개체를 하나씩 선택 집합에 넣고 있어, 개체마다 겹침 검사가 처음부터 다시 돌았다 — 비용이 선택 개수의 제곱으로 불어나 300개에 2.5초가 걸렸다(`03) 뷰 디버깅.md` 17번). 한 번에 대입하도록 고친 뒤 2,000개가 220ms다. **캐시 무효화를 `didSet`에 모은 구조에서는 그 상태를 반복 갱신하는 자리가 곧 성능 함정이다**
- **`FeatureStore.indexByID`는 `CodingKeys`와 `==`에서 제외한다.** 파일 형식이 갈리지 않게, 그리고 `perform`의 "바뀐 게 없다" 판정이 달라지지 않게 하기 위해서다
- **실행취소 스냅샷(제안 7)은 손대지 않았다.** 측정값이 feature 300개에서 0.01 ms/회라 고칠 이유가 없다. `--selftest`가 이 수치를 계속 감시한다

#### 지도 마커 십자 전환과 드래그 축척 문제 (2026-08-26 보고, 수정 완료)
`AnchorMapMarker.swift`·`AnchorMapMath.swift`(신규, `UI/Anchor/`)

**보고된 증상:** 이미 찍힌 마커를 아주 조금 드래그했는데 Anchor가 몇 km를 움직인다. 지도 축척이 반영되지 않는 것처럼 보인다.

**원인은 두 가지였고 둘 다 축척과는 무관했다.**

1. **집는 순간의 순간이동.** 드래그가 마커를 커서 좌표에 **그대로 대입**하고 있었다(`env.updateAnchorGeo(id, to: coord)`). 마커를 집는 판정 반경이 22pt인데, 넓게 축소한 지도에서 22pt는 실제로 몇 km다. 즉 커서를 움직이기도 전에 **집는 순간 그만큼 튄다.** → `AnchorMapMath.grabOffset`으로 "집은 지점 → 마커 중심"의 차이를 기억하고, `draggedCoordinate`가 그 차이를 유지한 채 옮긴다. 이제 마커는 커서가 움직인 만큼만 움직인다
2. **카메라가 `.automatic`으로 남아 있었다.** `MapCameraPosition.automatic`은 표시 중인 내용(마커·겹쳐 놓은 도면 폴리라인)에 맞춰 지도가 **스스로 화면을 다시 잡는다.** 그 상태로 마커를 끌면 마커가 움직일 때마다 지도가 다시 맞춰지고, 커서 아래 좌표가 매 프레임 달라져 **마커가 점점 멀리 달아난다.** 겹쳐보기까지 켜져 있으면 도면 전체가 마커를 따라 움직이므로 재조정 폭이 더 커진다. → `pinCameraIfNeeded()`가 화면 진입 시·첫 쌍 생성 시 현재 범위(또는 `AnchorMapMath.regionFitting`)로 카메라를 못 박고, 마커를 집는 순간에도 다시 못 박는다. `focusCamera()`·검색 결과 이동도 `didPinCamera`를 세운다

**마커 모양(사용자 요청):** 지름 14pt 원(블루닷) → **도면 쪽과 같은 십자 + 작은 원 + 번호**. 원은 중심이 어디인지 눈으로 특정할 수 없어 건물 모서리에 맞추는 정밀 조정에 쓸 수 없다 — **마커가 가린 자리가 곧 찍어야 할 자리**이기 때문이다. 십자는 선이 만나는 한 점이 좌표이고 그 주변이 가려지지 않는다. 도면(`AnchorDrawingPane.drawMarker`)과 모양을 같게 둔 것도 목적이다 — 두 화면에서 같은 지점을 짝지어야 하는데 모양이 다르면 무엇과 무엇을 맞추는 중인지 대조하기 어렵다. 위성 이미지 위에서 묻히지 않도록 **흰 선(3.6pt)을 굵게 깔고 그 위에 색(1.6pt)을 얹는다**. 마커는 `allowsHitTesting(false)` — 마커가 클릭을 먹으면 마커를 집는 드래그가 지도까지 닿지 않는다

- 검증: `--selftest`에 5항목 신규(집기만으로는 안 움직임 · 커서가 움직인 만큼만 움직임 · 고정 범위가 Anchor 전부를 담음 · 한 점뿐일 때 최소 300m · Anchor 없으면 고정 안 함). **드래그 자체는 GUI라 눈 확인이 필요하다**
- 갱신 파일: `UI/Anchor/AnchorMapMarker.swift`(신규) · `UI/Anchor/AnchorMapMath.swift`(신규) · `UI/Anchor/AnchorScreen.swift`(`mapGesture`·`pinCameraIfNeeded`) · `App/SelfTest.swift`

#### 지도 장소 검색 (2026-08-26 요청, 구현 완료)
`PlaceSearch.swift`(`UI/Anchor/`) — 지도 위쪽 검색줄에 건물·주소 이름을 넣으면 그 자리로 지도가 이동한다. 위성 이미지만으로 목표 건물을 찾으려면 도면 하나마다 지도를 손으로 끌어야 했다.

- **검색은 지도를 옮기기만 한다. Anchor 쌍은 만들지 않는다.** MapKit이 돌려주는 좌표는 건물 대표점(입구·중심)이라 도면의 특정 모서리와 대응하는 점이 아니다. 그 점을 그대로 Anchor로 넣으면 **어디에 대응하는지 모르는 쌍**이 생기고, 잔차는 그 쌍까지 포함해 계산되므로 정합이 조용히 나빠진다. 쌍을 만드는 경로는 지금까지대로 도면 클릭 → 지도 클릭뿐이다
- **검색 편향은 지금 보고 있는 지도 범위다.** `.onMapCameraChange(frequency: .onEnd)`로 현재 범위를 받아 `MKLocalSearch.Request.region`에 넣는다. "제2공학관"처럼 전국에 같은 이름이 여럿인 검색어에서 화면 근처가 먼저 나온다
- **이동 배율을 150~1200m로 조인다**(`PlaceSearchModel.clampMeters`). MapKit이 주는 장소 범위를 그대로 쓰면 대학·병원 같은 넓은 부지에서는 캠퍼스 전체가 잡혀 다시 확대해야 하고, 점 하나짜리 관심지점에서는 지나치게 당겨져 주변을 잃는다. **Anchor 작업은 건물 모서리를 특정할 수 있는 배율에서만 가능하므로** 그 범위를 벗어나지 않게 한다
- **앞선 검색을 반드시 취소한다**(`running?.cancel()` + 응답 도착 시 `running === search` 확인). 취소하지 않으면 두 응답이 순서 없이 도착해 **옛 검색 결과가 새 결과를 덮어쓴다**
- **실패 문구를 두 갈래로 나눈다.** "결과가 없습니다"(검색어를 고칠 일)와 "인터넷에 연결되어 있지 않습니다"(연결을 확인할 일)는 사용자가 할 일이 다르다. `MKError.placemarkNotFound`·`serverFailure`·`loadingThrottled`와 `NSURLErrorDomain`을 구분한다
- **결과 목록은 Anchor 찍기용 투명 겹침보다 뒤에 얹는다.** 앞에 두면 목록이 그 겹침(`Color.white.opacity(0.001)` + 제스처)에 가려져, 목록을 클릭한 것이 지도 클릭으로 새 나간다
- 검증: `--selftest`에 순수 계산 5항목 신규(검색어 정규화 · 넓은 장소 배율 상한 · 점 장소 배율 하한 · 이동 중심 좌표 · 실패 문구 구분). 네트워크가 필요한 검색 자체는 `--selftest`로 돌릴 수 없어 **실제 검색 동작은 눈 확인이 필요하다**
- 갱신 파일: `UI/Anchor/PlaceSearch.swift`(신규) · `UI/Anchor/AnchorScreen.swift`(`searchBar`·`searchResultList`·`visibleRegion`) · `App/SelfTest.swift`

### 2.15-2 다각형 선택 — 폴리곤 type 레이어의 기본 화면 (신기능 5항 + 5-4 전환, 2026-08-26)

`Geometry/ClosedPolygonFinder.swift` · `App/ClosedPolygon.swift` · `UI/ClosedPolygon/ClosedPolygonAppearance.swift`·`PolygonToolbar.swift` · `UI/HoverNote.swift` · `Model/FeatureGroup.polygonRings`

> **전용 창은 없앴다(2026-08-26 2차).** 처음에는 별도 전체화면이었으나, 다각형 선택이 **선분 선택을 대체**하기로 하면서 폴리곤 type 레이어의 기본 화면이 됐다. `ClosedPolygonScreen`·`ClosedPolygonPane`은 삭제되고 그 그리기가 `UI/CanvasView.swift` 안으로 들어갔다.

#### 캔버스가 두 모드로 갈린다
- **폴리곤 type**(unit·footprint·level·venue·section·geofence·fixture) → 면을 고른다
- **LineString(opening)·Point(amenity·anchor)** → **선분 선택 그대로**다(5-4 1번 결정). 그래서 `UI/SelectionToolbar.swift`·`UI/MarqueeSelection.swift`·`UI/SelectModifierMonitor.swift`·`Geometry/HitTester.swift`는 지우지 않았다
- 갈림의 기준은 `AppEnvironment.isPolygonWorkMode` 한 곳이다. 캔버스 그리기·클릭·드래그·상단바가 모두 이 값을 본다 — **분기 조건이 흩어지면 어떤 화면에서는 면이, 어떤 화면에서는 개체가 잡히는 상태가 생긴다**

#### 포함 / 제외 두 모드
- 포함은 빈 상태에서 더해 가고, 제외는 **전부 고른 상태에서 빼 나간다.** 저장할 것이 대부분일 때 제외 모드가 훨씬 빠르다
- **두 모드 모두 '선택한 다각형 모두 저장' 하나로 끝난다.** 모드는 선택을 만드는 방법이 다를 뿐 결과가 같다
- 상단바가 `고른 수 / 고를 수 있는 수`를 함께 보여준다 — 제외 모드에서 남은 개수만 보이면 얼마나 뺐는지 알 수 없다
- **드래그는 뒤집지 않는다.** 포함은 더하고 제외는 뺀다. 수십 개가 한꺼번에 뒤집히면 결과를 예측할 수 없다(선분 드래그 선택과 같은 규칙)

#### fixture — 맞닿은 면 묶기
`ClosedPolygonFinder.connectedGroups` — 변을 나눠 쓰는 면들을 union-find로 이어 한 덩어리로 만든다. MultiPolygon인 fixture는 덩어리 하나가 feature 하나다. **폴리곤 type은 이 함수를 쓰지 않는다** — 방 둘이 벽을 나눠 쓴다고 한 방이 되면 안 된다.


**작업 순서를 뒤집는 기능이다.** 지금까지 폴리곤 type은 벽선을 하나씩 골라 묶었고 링이 열린 것을 저장한 뒤에야 알았다(명세 10-4). 이 창은 **이미 닫혀 있는 면을 전부 찾아 보여주고** 사용자는 고르기만 한다.

#### `ClosedPolygonFinder`
평면 그래프의 면 추적. 선분 자르기 → 마디 합치기 → 각도 정렬 → 최소 순환 추적 → 부호로 바깥 면 제거.
- **T자 접합을 반드시 자른다.** 방을 가로지르는 벽은 양 끝이 바깥 벽의 **중간**에 붙는다. 교차 판정을 "양쪽 모두 내부"로 두면 이 접합이 잘리지 않아 두 방이 한 덩어리로 남는다. `crossing`이 양쪽 매개변수를 돌려주고, **각자 내부인 쪽만** 자른다
- **같은 두 마디를 잇는 선은 한 번만 쓴다.** 겹쳐 그린 벽선을 그대로 두면 같은 면이 겹친 수만큼 중복된다
- **넓이 4 미만은 버린다.** 벽 두께 사이의 자투리까지 보여주면 고를 것이 수백 개가 된다
- **창에 들어갈 때 한 번만 만든다.** 자르기가 선분 수의 제곱이라 도면 적재 시점에 만들면 앱 시작이 멈춘다 — 신기능 3항에서 이미 한 번 겪은 실수다. 경계 상자로 먼저 거르고, 격자 도면(면 576개) 0.00초를 자체점검이 지킨다

#### `FeatureGroup.polygonRings` — geometry의 정본
(fixture는 링이 여럿이라 배열이다. 내보내기는 링마다 따로 변환한다 — 한 줄로 이으면 서로 다른 면이 하나의 링으로 뭉개진다.)
**옆방과 벽을 나눠 쓰는 것이 이 기능의 핵심 제약이다.** 맞닿은 벽선 하나를 두 방이 함께 쓰는 것은 도면에서 정상인데 소유권은 배타적이라(명세 4-1), 두 번째 방은 그 벽선을 구성원으로 가질 수 없다. 그 상태로 구성원만 이으면 벽 하나가 빠진 열린 링이 된다.
- 그래서 **주인 없는 개체만 소유를 주장하고**, 이미 남이 가진 벽선은 좌표만 빌려 쓴 것으로 본다(명세 10-2 opening 빌려주기와 같은 발상)
- 대신 화면에서 닫힌 것을 확인하고 고른 **면의 좌표를 정본으로 싣는다**. `VertexExtractor`가 polygon·multiPolygon일 때 이 값을 먼저 본다(`closureSegment`가 opening에서 하는 역할과 같다)
- **이 완화는 명세 4-1의 배타성을 한 군데 무르게 한 것이라 사용자 확인 대상이다**(`06) 확인 필요.md` A13)

#### 화면 (지금은 메인 캔버스 안)
- **면 → 선 → 점 순서로 겹쳐 그린다. 순서가 곧 규칙이다** — 면을 나중에 그리면 경계선과 꼭짓점을 덮어 어디서 닫혔는지 확인할 수 없다
- 색은 `ClosedPolygonAppearance`에 모으고 **셋이 서로 다른 색인지를 자체점검이 확인한다**(`AuxiliaryOpacity`·`DoorClosureAppearance`와 같은 규칙 — 뷰 안에 박힌 색은 검증할 수 없다)
- **클릭은 겹친 면 중 작은 쪽을 고른다.** 방은 건물 외곽 안에 있어 늘 겹치는데, 큰 쪽을 고르면 방을 누를 때마다 건물 전체가 잡힌다
- 안내 팝업에 **'보조 개체 제외 창 열기' 버튼**을 함께 뒀다. 자투리 면이 너무 많다는 것이 이 기능의 실패 모드이고, 그 처방이 보조 개체 제외이기 때문이다 — 문장으로만 알려주면 창을 나가 메뉴를 다시 찾아야 한다
- **저장은 실행취소 대상이고, 되돌리면 고르던 면도 함께 돌아온다**(`EditorSnapshot.faceSelection`). 그래야 "저장을 취소했다"가 성립한다. 개별 선택 토글은 종전처럼 되돌림 대상이 아니다(A6)
- **면 찾기는 레이어를 열 때와 보조 개체 제외가 바뀔 때만** 한다. 매 프레임도, 도면 적재 시점도 아니다
- **진행률 막대가 둘이다**(신기능 5-5). 개체 기준과 다각형 기준. 다각형 막대의 분모는 **보조 개체로 만들어지는 면까지 포함해 도면을 열 때 한 번** 세고, 보조 개체를 빼면 분모가 줄지 않고 '제외로 사라진 다각형'으로 **분자에 얹힌다**. 두 막대 모두 마우스를 올리면 `UI/HoverNote.swift`의 반투명 검정 안내 창이 뜬다 — 시스템 툴팁은 뜨기까지 1초 넘게 걸리고 두 줄 넘는 문장이 잘려서 쓰지 않았다

### 2.15-3 UI/Curved/ — 곡선 개체 전용 화면 (명세 3-3, 2026-08-27)

`App/CurvedWork.swift` · `UI/Curved/CurvedScreen.swift`·`CurvedDrawingPane.swift`

> **모드에서 전용 창으로 바꾼 이유**(`03) 뷰 디버깅.md` 18번). 메인 캔버스의 모드였을 때 눌렀을 때의 변화가 **'곡선 아닌 개체 75%'뿐**이라 사용자에게는 아무 일도 일어나지 않는 버튼으로 읽혔다. 폴리곤 type 레이어가 면 선택 화면이 된 뒤로는 **클릭이 면을 고르므로 곡선을 고를 수조차 없었다** — 선분화 대상 지정이 이 기능의 목적인데 그 경로가 막혀 있었다. 명세 3-3의 원문도 "창이 열림"이다.

- **직선·곡선·선분화된 곡선을 색으로 가른다**(회색 / 주황 / 초록). 옅기 차이만으로는 무엇이 곡선인지 알 수 없다. 색은 `CurvedAppearance`에 모으고 **둘이 다른 색인지를 자체점검이 확인한다**(`AuxiliaryOpacity`·`DoorClosureAppearance`와 같은 규칙)
- **이 창에서는 곡선만 고를 수 있다**(명세 3-3-2). 직선까지 고를 수 있으면 '선택 선분화'가 아무 일도 하지 않는 경우가 생겨 사용자는 고장으로 읽는다
- 클릭 허용 반경은 8pt로 메인 캔버스(6pt)보다 넉넉하다 — 곡선은 선이 가늘어 겨냥이 어렵다

- **나갈 때 모드와 선택을 함께 정리한다.** 선택을 남기면 메인 화면에서 곡선이 골라진 채로 시작해, 그 상태로 'Feature로 저장'을 누르면 의도하지 않은 태깅이 된다
- 곡선이 없는 도면에서는 버튼을 **비활성으로 두고 이유를 도움말로 밝힌다**

### 2.15-1 UI/Auxiliary/ — 보조 개체 제외 전용 화면 (디버깅 6번, 2026-08-25)

Anchor 화면과 같은 이유로 시트가 아니라 **전체 화면 전환**이다. 도면 전체를 훑으며 수십 개를 골라내는 작업이라 화면이 넓어야 한다.

#### `AuxiliaryScreen.swift`
좌: 도면 패널 / 우: 창 전용 사이드바 / 상단: 제목 줄 + (선택이 있을 때) 개체 선택 상단 바.
- 상단 바: `보조 개체로 지정` · `똑같이 생긴 개체 모두 표시`(토글) · `똑같이 생긴 개체 모두 지정` · `지정 풀기` · 선택 해제
- 우측 사이드바: 세그먼트 두 탭 — `똑같이 생긴 그룹`(크기 2 이상) / `개별 개체`(크기 1). 둘 다 `twinGroups`를 **많은 것부터** 정렬한 것에서 갈라 온다(보조 개체는 반복 개수가 많아 위쪽 몇 개가 곧 작업 대상이다). 행을 누르면 그 대상만 100%, 나머지는 75% — 아래 "그룹 / 개별 개체 분리" 참조
- `모든 보조 개체 제외` — 지정된 개체가 하나라도 있는 쌍둥이 그룹을 **그룹 전체** 제외한다. 명세 문구("지정된 모든 보조 개체 **및 똑같이 생긴** 보조 개체 그룹들")를 그대로 따른 것이다. **(2026-08-25 2차, 사노 결정으로 해소)** 일부만 보조인 그룹에서 과할 수 있다는 우려에 사노는 "그룹 전체를 제외하더라도 오른쪽 사이드바에서 다시 복구 가능하게" 하라고 답했다 — 확인해 보니 **이미 그렇게 동작한다.** 그룹 행을 클릭하면 그 그룹 멤버 전체가 선택되고(`groupRow.onTapGesture`), 그중 제외된 것이 있으면 상단바에 `지정 풀기`가 나타나 `unmarkSelectedAsAuxiliary`로 그룹 전체를 되살릴 수 있다. 추가 구현 불필요.
- 75% opacity 규칙이 여러 곳에 흩어지지 않도록 `AuxiliaryOpacity.value(for:highlighted:)` 한 곳에서 계산한다

##### 쌍둥이 인덱스 — 화면이 멈추던 건 (엔진 디버깅 1-1번, 2026-08-25)
`똑같이 생긴 개체 모두 보기`를 누르면 커서가 로딩 상태에서 돌아오지 않았다. **무한 루프가 아니라 계산량 폭발이었다** — 기다리면 언젠가 끝나므로 앱은 죽지 않고 커서만 돌았다.

- **원인 구조:** `twinKey`가 비싼데(위 2.3절 경고) `twins(of:)`·`twinGroups`가 **계산 프로퍼티**라 부를 때마다 도면 전체의 키를 새로 만들었고, 캔버스가 `auxiliaryOpacity(for:)`를 **개체마다** 부르면서 그 안에서 또 `twins(of:)`를 불렀다. 결과는 매 프레임 **O(N² × 점 개수)**
- 실측(디버그 빌드, 개체 600개): 옛 방식이면 30프레임에 **약 100초**. 실도면은 개체가 수천 개라 제곱으로 더 늘어난다
- **고친 원칙: 키는 도면이 바뀔 때만 바뀐다.** 적재 순간 한 번 만들고 이후에는 사전 조회만 한다
	- `private(set) var twinKeyByObject: [VectorObjectID: String]` · `private var twinMembersByKey: [String: Set<VectorObjectID>]` · `@Published private(set) var twinGroups: [TwinGroup]`(정렬 완료)
	- `private func rebuildTwinIndex()` — **`document`의 `didSet`이 유일한 호출자다.** 다른 곳에서도 부를 수 있게 두면 "언제가 최신인가"가 흐려져 매 프레임 재계산으로 되돌아간다
	- `func twins(of:)`는 이제 사전 조회 두 번뿐이다
- **`var auxiliaryHighlightedIDs: Set<VectorObjectID>?`** — 지금 100%로 보여야 할 개체. `nil`은 "강조가 꺼져 있어 전부 100%"라는 뜻이다. **캔버스는 이 값을 그리기 루프 *바깥*에서 한 번만 받는다** — 개체마다 다시 물으면 개체 수만큼 집합을 새로 만들게 되어, 인덱스를 만들어 놓고도 같은 문제가 다시 난다
- `enum AuxiliaryOpacity` — `focused` 1.0 / `dimmed` 0.75와 판정 함수. **뷰에서 떼어낸 이유는 검증 때문이다:** 명세의 75%가 뷰 안에 박혀 있으면 `--selftest`가 확인할 방법이 없다
- **재발 방지선:** `--selftest`에 "개체 600개 도면 30프레임 1초 이내" 항목을 뒀다. 고치기 전이라면 이 한 항목만으로 100초가 걸려 확실히 걸린다. 캐시가 직접 계산과 일치하는지도 함께 본다 — 캐시가 어긋나면 화면에 100%로 보이는 것과 실제 지정 대상이 갈라진다

##### `똑같이 생긴 개체 모두 표시` — 복수 선택 지원 (엔진 디버깅 1-2번, 2026-08-25)
`AppEnvironment.canShowTwins` (= `!auxiliarySelection.isEmpty`). 표시 버튼·지정 버튼·배율 계산이 **모두 이 하나를 본다** — 조건을 세 곳에 따로 쓰면 화면에 100%로 보이는 것과 실제로 지정되는 것이 갈라진다.

> **⚠️ 뒤집힌 결정.** 처음(뷰 디버깅 11번, 2026-08-25)에는 `count == 1`로 제한했었다. 근거는 "여럿을 고르면 서로 다른 쌍둥이 그룹이 섞여 100%가 합집합이 되고 '무엇과 똑같은가'의 기준이 사라진다"였다. **사용자 요청으로 같은 날 뒤집었다**(엔진 디버깅 1-2번). 아래 문단이 지금의 판단이다 — `count == 1`로 되돌리려는 세션이 있다면 여기부터 읽을 것.

- **근거는 맞았고 대응이 틀렸다.** 합집합이 되는 건 사실이지만, 실제 작업은 "치수 숫자 3종을 한꺼번에 골라 통째로 빼기"처럼 여러 그룹을 동시에 다루는 쪽이 훨씬 흔했다. 제약은 그때마다 그룹 하나씩 반복하게 만든다. **기준이 흐려지는 게 문제라면 막을 게 아니라 기준을 화면에 띄우면 된다**
- **`enum TwinToggleText`** — 버튼 라벨과 도움말을 만드는 순수 함수. 켜져 있으면 `쌍둥이 3그룹 · 24개 표시 중`으로 **그룹 수와 총 개수를 함께** 보여준다(그룹이 1이면 "1그룹"은 뜻 없는 숫자라 빼고 `쌍둥이 6개 표시 중`). **뷰에서 떼어낸 이유는 `AuxiliaryOpacity`와 같다 — 검증이다.** 화면이 합집합이라는 사실을 말해 주는 게 이번 완화의 **전제 조건**이라, 라벨이 문자열 보간으로 뷰에 박혀 있으면 `--selftest`가 확인할 방법이 없다
- **`var selectedTwinGroupCount`** — 선택이 걸친 **고유 키 개수**. 같은 그룹에서 여럿을 골라도 1로 센다
- **자동 해제는 "선택이 0개가 될 때"로 좁혔다.** `didSet`의 원래 목적은 "켜져 있는데 끌 버튼이 없는 상태"를 막는 것이었다(「디버깅 완료」 2번, 접으면 못 펴는 사이드바와 같은 함정). 2개여도 버튼이 살아 있으니 끌 방법이 있다. 선택이 **비면** 상단바 자체가 사라지므로 그때만 끈다 — 함정이 없어진 게 아니라 발동 조건이 좁아진 것이라 `didSet`은 그대로 뒀다
- **버린 대안 — "여러 그룹이면 첫 그룹만 기준으로":** 기준이 하나로 유지돼 깔끔하지만 사용자가 고른 3개 중 2개가 75%로 흐려진다. 방금 자기가 고른 게 흐려지는 건 고장으로 읽힌다
- **우측 사이드바의 그룹 목록(`focusedTwinKey`) 경로는 제한하지 않는다.** 그쪽은 그룹을 직접 지목하는 것이라 "무엇과 똑같은가"가 애매해질 여지가 없다

##### 우측 사이드바 — 그룹 / 개별 개체 분리 (엔진 디버깅 1-3번, 2026-08-25)
예전 목록 조건은 `twinGroups.filter { $0.count > 1 || 제외된 게 있으면 }` 하나뿐이라 **쌍둥이가 없는 개체(그룹 크기 1)는 아예 안 보였다.** 도면에 하나뿐인 방위표·범례·제목 박스는 목록에서 찾을 방법이 없어 도면을 눈으로 훑는 수밖에 없었다.

- **`enum AuxiliarySidebarTab`(`.twinGroups` / `.soloObjects`) + `func auxiliarySidebarGroups(_:)`.** 나누는 판정을 **뷰의 `filter`가 아니라 `AppEnvironment`에** 둔 이유: 어느 개체가 어느 탭에 뜨는지는 판정 규칙이라 `--selftest`가 봐야 한다. 뷰에 박아 두면 이번 같은 "한쪽이 통째로 안 보임"이 또 나도 못 잡는다
- **세그먼트 전환(`Picker` + `.segmented`)을 골랐다. 버린 대안은 두 섹션 쌓기** — 만들기는 쉽지만 개별 개체는 실도면에서 수백 개까지 늘어나 그 목록이 그룹 목록을 스크롤 밖으로 밀어낸다. 정작 작업량이 큰 쪽(반복이 많은 그룹)이 안 보이게 되는 뒤집힌 우선순위다. 두 목록은 답하는 질문도 다르다 — 그룹은 "무엇이 반복되는가", 개별은 "무엇이 안 묶였는가"
- **탭 이름에 개수를 붙인다.** 보고 있지 않은 쪽의 규모를 알아야 "여기 없으면 저기 있겠구나"가 성립한다
- **두 목록은 겹치지 않고 합치면 도면 전부다**(크기 2 이상 / 크기 1). 겹치면 같은 개체가 두 탭에 나와 "그룹인가 개별인가"가 흐려진다. 예전 조건의 `|| 제외된 게 있으면`은 뺐다 — 크기 1짜리를 그룹 탭에 끌어오려던 임시방편이었다. 제외된 개체를 되살리는 경로(행 클릭 → `지정 풀기`)는 개별 탭에서 그대로 된다
- **개별 개체용 강조 상태를 새로 만들지 않았다.** 크기 1짜리 그룹의 키는 그 개체 하나만 가리키므로 `focusedTwinKey` 하나로 두 탭이 다 된다. 따로 두면 강조 대상이 두 군데서 정해져 `auxiliaryHighlightedIDs`가 "둘 중 뭘 먼저 보나" 규칙을 또 만들어야 한다
- 개별 탭 행은 `직선 × 1` 대신 모양 이름만, 제외 배지도 `1/1 제외` 대신 `제외됨`. 하나뿐인 게 그 탭의 전제라 숫자가 뜻을 못 갖는다
- **재발 방지선:** `--selftest`의 "모든 개체가 어느 한 탭에는 뜬다". 예전 조건이라면 이 항목에서 걸린다

##### 지정이 끝나면 선택을 비운다 (엔진 디버깅 1항, 2026-08-25)
`markSelectedAsAuxiliary`·`markTwinsAsAuxiliary`가 `auxiliary.exclude` 직후 `auxiliarySelection`을 비운다. (`markTwinsAsAuxiliary` 쪽은 엔진 디버깅 1-4번에서 뒤늦게 맞췄다 — 앞쪽만 고쳐 두 지정 버튼의 동작이 갈라져 있었다.)
- **쌍둥이 지정 쪽이 더 심하다.** 한 번에 그룹 전체가 나가므로 방금 지정한 수십 개가 통째로 남고, 다음 개체를 하나 더 고르면 선택이 수십 개짜리가 되면서 라벨의 그룹 수까지 어긋난다
- **`focusedTwinKey`는 일부러 안 건드린다.** 우측 목록에서 그룹을 지목해 들어온 흐름이면 방금 무엇을 지정했는지가 100%로 남아 있어야 결과를 눈으로 확인할 수 있다. **선택(작업 대상)과 강조(보고 있는 대상)는 뜻이 다르다**
- **지정은 이 창에서 선택의 종착점이다.** 보조 개체로 지정하면 그 개체는 태깅 대상에서 빠지므로 더 할 일이 없다. 골라 둔 채로 두면 다음 개체를 고를 때 이전 것이 합쳐져 이미 지정된 것을 또 지정하게 된다 — `exclude`는 집합 연산이라 결과는 같지만, 화면의 `N개 선택`이 실제 작업 대상과 어긋난다
- **`unmarkSelectedAsAuxiliary`('지정 풀기')는 비우지 않는다.** 푼 개체를 이어서 다시 보거나 태깅하러 가는 흐름이 정상이라 선택이 남아 있어야 한다. 종착점인 쪽만 비운다
- 선택이 비면 위 `didSet` 규칙이 그대로 작동해 `showTwinsOnly`도 함께 꺼진다. 따로 손댈 곳이 없었고 자체점검으로 못박았다
- **기존 자체점검이 이 변경으로 조용히 무력화될 뻔했다.** 시험이 `markSelectedAsAuxiliary` 직후 `markTwinsAsAuxiliary`를 부르고 있었는데, 선택이 비면 `canShowTwins`가 거짓이라 guard에 걸려 아무 일도 하지 않고 통과한다. 쌍둥이 확장 전에 다시 고르도록 고치고 이유를 시험 코드에 주석으로 남겼다

#### `AuxiliaryDrawingPane.swift`
창 전용 도면 패널. 그룹화·소유권이 없고 제외 표시만 한다.
- **선택 방식이 메인 캔버스와 다르다.** fn+shift+z 없이 그냥 클릭해도 선택된다 — 이 창에 들어온 목적 자체가 고르는 것이라, 메인 화면의 실수 방지 장치가 여기서는 방해만 된다. 드래그는 팬
- 제외된 개체는 **사라지지 않는다**(명세 2항). `CanvasBackground.excludedStroke` + 40% opacity + bounding box 사선으로 상태만 드러낸다. 옅게만 두면 '아직 안 고른 것'과 구별이 안 되기 때문
- `excludedStroke`는 `disabledStroke`(회색)와 **일부러 다른 색**이다. 비활성은 "다른 type이 이미 가져갔다", 제외는 "아무도 안 가져간다"로 뜻이 정반대다

#### 전체 선택 해제 확인 (디버깅 7번, 2026-08-25)
`AppEnvironment.ClearSelectionTarget`(`.main` / `.auxiliary`) + `pendingClearSelection` + `requestClearSelection(_:)`·`confirmClearSelection()`·`cancelClearSelection()`.

> 좌측 사이드바에 '곡선 개체만 따로 보기' 버튼을 추가합니다. 클릭하면, 곡선 개체를 제외한 모든 개체가 75% opacity로 표시되는 창이 열립니다. X 버튼 클릭 시 닫기 가능. 이미 선분화된 곡선 개체도 함께 표시됩니다.
> 곡선 개체만 따로 보기 창 안에서, 각 곡선 개체를 개별적으로 선택하여 '선분화' 가능합니다.
> 곡선 개체만 따로 보기 창 안에서, '선분화된 곡선 개체만 보기' 클릭 시 모든 곡선 개체가 50% opacity로 표시되며, 그 위에 선분화된 곡선 개체만 100% opacity로 선명하게 표시됩니다. 선분화된 곡선 개체를, 기존 곡선 개체 단위로 선택 가능합니다. 이때, 선택 시 '선분화 해제' 가능합니다.
