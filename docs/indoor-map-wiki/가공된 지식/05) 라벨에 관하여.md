## 답변

출처: `src04. IMDF 공식 스펙 — 라벨·Name·Display Point 필드 조사.md` (IMDF 1.0.0 공식 스펙, OGC Community Standard 문서 `docs.ogc.org/cs/20-094` 조사 기준)

### GQ1. 라벨은 어떤 타입인가? 위도 경도 좌표 및 벡터와 별도의 공간에 저장되나?

- IMDF에는 "Label"이라는 이름의 독립 Feature Type이 없다. 전체 16개 Feature Type(Address, Amenity, Anchor, Building, Detail, Fixture, Footprint, Geofence, Kiosk, Level, Occupant, Opening, Relationship, Section, Unit, Venue) 목록에 포함되지 않는다.
	- **Feature Type이란?** -- 모든 IMDF Feature 객체는 최상위에 `feature_type`이라는 필드를 갖고, 그 값은 반드시 위 16개 문자열(소문자: `unit`, `opening`, `level` 등) 중 하나여야 한다(Reference 원문: "The value of a Feature's `"feature_type"` member MUST be one of the following case-sensitive values:"). 즉 "Feature Type"은 그 Feature가 무엇을 나타내는지(방인지, 문인지, 층인지 등) 표시하는 분류 값이다. 스펙에 "A Feature Type is..." 같은 별도 정의 문장은 없고(확인 필요), 이 규정을 통해서만 역할이 드러난다.

- "라벨"에 해당하는 것은 Unit·Kiosk·Amenity·Section·Opening·Occupant 등 각 Feature의 `properties` 안에 있는 `name`/`alt_name` 속성이며, 데이터 타입은 **LABELS**다.
	- **Feature의 properties 안에 있다는 게 뭔지? 코드로 보여줘라.** -- 아래는 Unit 스펙 페이지(docs.ogc.org/cs/20-094/Unit)에 실린 공식 예시 JSON 그대로다(자체 생성 아님).

```jsonc
{
  "id": "11111111-1111-1111-1111-111111111111",
  "type": "Feature",
  "feature_type": "unit",
  "geometry": {
    // 도형(좌표)은 이 블록 안에만 있다 — Unit이 차지하는 폴리곤
    "type": "Polygon",
    "coordinates": [
      [[100.0, 0.0], [101.0, 0.0], [101.0, 1.0], [100.0, 1.0], [100.0, 0.0]]
    ]
  },
  "properties": {
    // "properties 안에 있다"는 말은 geometry가 아니라 바로 이 중괄호 { } 안에 들어있다는 뜻
    "category": "room",
    "name": {
      "en": "Ball Room"
      // ↑ 이게 라벨(name) LABELS 타입 — {"언어태그": "문자열"} 형태
    },
    "alt_name": null,
    "display_point": {
      "type": "Point",
      "coordinates": [100.0, 1.0]
      // ↑ 라벨을 그릴 좌표. 값은 Point 좌표지만 geometry가 아니라 properties 안에 있다
    },
    "level_id": "22222223-2222-2222-2222-222222222222"
  }
}
```

**Q. 이 코드가 IMDF 파일 내부의 실제 코드입니까?**

- 둘 다 맞다고도, 아니라고도 할 수 있다. 정확히는 다음과 같다.
	- **실제 원문이라는 점에서는 맞다.** 이 JSON은 IMDF 1.0.0 공식 스펙의 Unit 페이지(`docs.ogc.org/cs/20-094/Unit/index.html`)에 있는 "Example" 섹션 내용을 그대로 옮긴 것이다(내가 값을 지어낸 게 아니라 스펙 문서에 실제로 실려 있는 코드). `id`, `type`, `feature_type`, `geometry`, `properties`(`category`, `name`, `alt_name`, `display_point`, `level_id`) 같은 필드 이름과 중첩 구조는 실제 IMDF Unit Feature가 반드시 따라야 하는 스키마 그대로다.
	- **특정 건물의 실제 데이터라는 뜻은 아니다.** `"id": "11111111-1111-1111-1111-111111111111"`, `"en": "Ball Room"`, 좌표 `[100.0, 0.0]` 같은 값들은 스펙이 필드 구조를 설명하려고 만든 예시(placeholder) 값이다. 실제 공항·쇼핑몰이 Apple에 제출한 진짜 IMDF 파일 안의 값이 아니다(예: 앞서 확인한 LABELS 타입 설명의 `{"en": "red", "es": "rojo", ...}` 예시도 마찬가지로 스펙이 만든 샘플이다).
	- 정리: **필드 구조·타입은 실제 규격 그대로**이고, **구체적 값(UUID·좌표·이름)은 스펙이 설명용으로 만든 예시**다.

- LABELS 원문 정의: "Labels are JSON objects used to capture a single lexical label for an entity in one or more explicitly stated languages." — 언어 태그(예: `en`, `en-US`)를 key로, `STRING` 값을 담는 JSON 객체다. 좌표나 벡터 타입이 아니라 문자열 딕셔너리 타입이다.
	- 

- 저장 위치: name(LABELS)은 Feature의 `properties` 멤버에 저장되고, 위경도 좌표(도형)는 같은 Feature의 `geometry` 멤버에 저장된다. 즉 라벨 텍스트는 좌표(geometry)와는 다른 멤버(properties)에 저장된다. 

- 라벨을 화면 어디에 그릴지 정하는 좌표 정보는 별도의 `display_point` 속성(타입: **DISPLAY-POINT**)으로 존재한다. 원문: "A Display Point represents a curated, Point-based representation of a non-puntal Feature." — GeoJSON Point 객체이며 "MUST be within the geometry of the Feature", "SHOULD be positioned in a location where map label 'collision' is least expected"로 규정된다. display_point도 `geometry` 멤버가 아니라 `properties` 멤버의 하위 항목이다("Display Points are members of a Feature's property object").

- 정리: name(라벨 텍스트, LABELS 타입)과 display_point(라벨을 놓을 좌표, DISPLAY-POINT 타입)는 서로 다른 두 속성이며, 둘 다 도형용 `geometry` 멤버가 아니라 `properties`라는 같은 공간 안에 나란히 존재한다. "라벨"이라는 단일 타입이 텍스트와 좌표를 함께 담는 구조는 아니다.

### GQ2. 라벨+GeoJSON은 하나의 배열에 함께 저장되나? 두 타입을 묶으면 어떤 타입이 되나?

- 라벨(name/alt_name)은 별도 배열이나 별도 GeoJSON 파일로 존재하지 않는다. Unit·Kiosk·Amenity·Section·Opening·Occupant 등 각 Feature Type 자체의 `properties` 안에 포함되어 있다.
- 하나의 Feature 객체(예: 하나의 Unit) 안에 geometry(폴리곤 좌표)와 properties(그 안에 `name`=LABELS, `display_point`=DISPLAY-POINT 포함)가 함께 들어있는 표준 GeoJSON Feature 구조다: `{"type": "Feature", "geometry": {...}, "properties": {...}}`.
- 여러 Feature가 모이면 GeoJSON FeatureCollection(배열)이 되며, IMDF 아카이브는 Feature Type별로 별도 `.geojson` 파일(FeatureCollection)로 나뉜다(WWDC19 전사문 및 src01 기준). 즉 "GeoJSON(도형)과 라벨을 묶은 결과"는 새 이름의 타입이 아니라, 해당 Feature Type의 GeoJSON Feature 객체 자체다(예: `name` 속성을 가진 Unit Feature 하나).
- 확인 필요: 조사 범위(Reference 데이터 타입 목록, Unit/Kiosk/Amenity/Section/Opening/Occupant 정의) 안에서 "라벨+도형을 묶은 결과물"을 가리키는 별도 명칭(예: LabeledFeature 등)은 발견되지 않았다.

### GQ3. 카테고리 표시의 최소 단위는 무엇인가? 벽을 쪼개는 최소 단위는 무엇인가?

**(a) 카테고리 표시의 최소 단위**

- category도 name(LABELS)과 마찬가지로 Feature 객체 단위의 속성이다. 하나의 Feature가 가진 폴리곤·선·점 도형의 일부만 따로 떼어 별도 카테고리를 매기는 방식은 조사된 속성 정의 안에 없다 — 카테고리를 매길 수 있는 최소 단위는 "개별 Feature 인스턴스 하나"다.
- category 속성이 있는 것으로 확인된 Feature Type은 7종이다: Unit(UNIT-CATEGORY, Polygon), Section(SECTION-CATEGORY, Polygon), Fixture(FIXTURE-CATEGORY, Polygon), Geofence(GEOFENCE-CATEGORY, Polygon), Opening(OPENING-CATEGORY, LineString), Amenity(AMENITY-CATEGORY, Point), Occupant(OCCUPANT-CATEGORY, geometry `null`). 반대로 Kiosk·Anchor·Detail의 properties 정의에는 category 속성이 확인되지 않았다.
- 이 중 **Fixture**가 실질적으로 가장 작은 단위의 카테고리 부여 수단이다. Fixture 정의 원문: "A Fixture models the presence and approximate physical extent of a moveable or semi-permanent physical asset." Fixture는 Polygon geometry를 가지되 `unit_id` 같은 소속 Unit 참조 필드가 properties에 없고 `level_id`(Level 참조)만 필수로 갖는다 — 즉 하나의 Unit 폴리곤 자체를 쪼개는 게 아니라, 그 Unit이 차지한 공간 안(또는 위)에 기둥·가구 같은 더 작은 독립 Polygon을 추가로 얹어 그 작은 영역에만 별도 category를 매기는 방식이다.
- 정리: IMDF에서 카테고리의 최소 단위는 항상 "Feature 인스턴스 하나"이며, 더 세밀한 카테고리 구분이 필요하면 기존 Feature(예: Unit)의 도형을 쪼개는 것이 아니라 Fixture·Amenity처럼 더 작은 독립 Feature를 추가로 배치하는 방식을 쓴다. 이 결론은 조사된 속성 스키마(11번 항목, src04)에 근거하며, "Fixture가 Unit 내부의 더 세밀한 카테고리 표현을 위해 쓰인다"는 의도까지 스펙이 명시적으로 서술한 것은 아니므로(도형·필드 구조만 확인됨) 그 목적론적 해석은 확인 필요로 남긴다.

**(b) 벽을 쪼개는 최소 단위**

- IMDF 16개 Feature Type, Reference의 전체 데이터 타입 목록 어디에도 "Wall(벽)"이라는 이름의 독립 Feature Type·데이터 타입은 없다.
- "wall"이라는 단어가 등장하는 곳은 두 곳뿐이다: ① Unit 정의 — extent(범위)를 특징짓는 예시 중 하나로 "A barrier, such as a wall"이 언급됨. ② Glossary — Room 정의("separated by interior walls... exterior wall")와 Neighboring 정의("spaces separated by a wall or barrier")에서 개념 설명으로만 등장.
- Opening(LineString) Feature의 Geometry Capturing Rule 원문: "the Opening MUST cover a single Unit boundary where the modeled entrance should exist" — Opening은 반드시 하나의 Unit 경계(boundary) 위에서, 입구(entrance)가 있는 지점만을 선으로 표시해야 한다. Opening도 name(LABELS) 속성을 가진다.
- 확인 필요: "Unit 경계선 자체가 벽에 해당한다"고 스펙이 명시적으로 등치시키는 문장은 확인되지 않았다. Unit 정의는 "extent가 barrier·wall로 특징지어질 수 있다"고만 말할 뿐, boundary(경계)를 wall이라 직접 부르지는 않는다. 따라서 "벽을 쪼개는 최소 단위가 Opening이다"라는 결론은 스펙에 직접 명시된 문장이 아니므로 확정 답변으로 제시하지 않는다.
- 확정적으로 말할 수 있는 것은: IMDF는 벽을 독립 지오메트리로 모델링하지 않으며, 벽과 관련해 조각(segment) 단위로 명시적으로 존재하는 Feature는 Opening(하나의 Unit 경계 전체가 아니라 그중 입구 부분만을 잘라 표시하는 LineString)뿐이라는 점이다.
